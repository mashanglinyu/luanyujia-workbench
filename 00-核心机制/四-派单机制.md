# 四 · 派单机制 —— 多 AI 之间"把活交出去、并且确认对方真的做了"

> [一-协作机制](一-协作机制.md) 讲了"派单 ≠ 公告"这条**原则**。
> 这一篇讲**怎么把它做成机制**：一条活从"我要交出去"到"确认干完"的完整状态机，以及每一步的抓手。
>
> 为什么值得单独一篇：**多 AI 系统里最贵的浪费是"双方都在等对方"** —— 而且它没有任何报错。

---

## 1. 一条活的完整状态机

```
   ① 想出派单
        │  判据：这件事要对方**动手**吗？
        ├─ 不用动手 ⇒ 公告（只落盘，不唤醒）
        └─ 要动手   ⇒ ② 派单
                        │
                        ▼
   ② 投递（必须真唤醒）
        │  写清四件套：现象 + 照哪节做 + 做完跑什么验 + 回一句
        ▼
   ③ 已投递 ──（对方回执：结论 + 证据 + 落盘路径）──► ④ 已回执
        │                                                  │
        │ 超时没有任何回执                                  ▼
        └──► ⑤ 未回执（进"我发出没回"清单）          ⑥ 收尾知悉（最多 1 条）⇒ 销账
                                                          │
                                                          ▼
                                                        结束
```

**状态 ③→⑤ 这里是最容易漏的**：没有"未回执"这个状态，派单就等于扔进黑洞。

---

## 2. 派单 vs 公告：唯一判据

| | 派单 | 公告 / 知悉 |
|---|---|---|
| 对方要做什么 | **动手** | 只是知道 |
| 要不要唤醒 | ✅ **必须**（会花对方一轮） | ❌ 不唤醒（只落盘） |
| 判据（看句子就知道） | 「**请你改 / 派单 / 做完回一句 / 改完跑 xxx 复验**」 | 「以后就是这么办了 / 请注意一下」 |
| 预期回复 | 一条**带证据**的回执 | 无（⛔ 收到知悉一个字都不许回） |

**真实事故**：一天发出 36 条"通知"，其中只有 **8 条**真的发进了对方会话 ——
其余全躺在对方的记忆文件里，**要等机主点开那个面板才看得见**。
机主当时的原话是：「**你这边派单他们没反应啊**」。

> 这就是"公告"和"派单"混用一次的成本：**8/36 的执行率**，而且没人知道那 28 条卡住了。

---

## 3. 派单正文：四件套（缺一件对方就得追问）

```
① 现象    ：现在是什么样子（可观察的，不要形容词）
② 照哪做  ：哪份文档的哪一节 / 哪个工具（唯一出处，别让对方再猜）
③ 怎么验  ：做完跑哪个检查、看到什么算通过
④ 回一句  ：明确要回执，并写"我在等你的回执"
```

反例与正例：

| | 写法 |
|---|---|
| ❌ | 「索引有点乱，你整理一下」 |
| ✅ | 「`索引体检` 报 3 条未登记（a.md/b.md/c.md）。照 `二-标准化规范` §6.4 的登记格式补行。补完跑 `node 索引体检.mjs`，应 ⛔0。**我在等你的回执**。」 |

---

## 4. 回执：必须投递，且必须带证据

### 4.1 格式（一行头 + 结论 + 证据 + 落盘路径）

```
【不需要回执·知悉】结论：索引已补齐 3 条。
证据：`索引体检` 输出「⛔0 ⚠0 ✅4」；差异集合 = 我补的 3 行。
落盘：<DSH根>\引擎\场景项目信息\<场景>\_文件索引.md
```

### 4.2 三条硬规矩

| 规矩 | 为什么 |
|---|---|
| ⛔ **只在自己窗口说"我做完了" = 没交付** | 发起方收不到；判据是"对方知道了"，不是"我说了" |
| ⛔ **只说"好了"等于没说** | 没有证据的完成，是在要求对方相信你 |
| ⛔ **收到"知悉"不许回** | 回了就开新一条线，双方互相客气到烧钱 |

> 判据：**"活干完了但对方还不知道" = 没干完。**

---

## 5. 上限：为什么必须限量

| 上限 | 值 | 来源 |
|---|---|---|
| 同一件事的消息数 | **≤ 3 条**（派单 + 回执 + 收尾知悉） | 实测：AI 之间会无限礼貌，一天烧掉几十万 token |
| 单条长度 | ≤ 200 字 / ≤ 10 行 | 回执给指针，报告放文件里 |
| 末行 | `【结束】` | 明确"这条线到这儿"，避免对方再回 |
| 纯确认语 | ⛔ 不许发（收到/好的/谢谢） | 不携带信息，只是社交 |

**这就是"规矩 10：禁止无限对话"** —— 它不是洁癖，是成本控制。

## 6. 台账与销账：让"谁欠谁"变成可查的

一个最小台账（一行一条）：

```json
{ "hash": "a1b2c3…", "from": "场景A", "to": "场景B", "at": "2026-10-21 10:12",
  "kind": "派单", "delivered": "RPC-200", "ack": null }
```

配套两个查询（这就是"抓手"）：

| 查询 | 回答 |
|---|---|
| **我发出、还没人回的** | 我欠不欠催？ |
| **别人在等我回的** | 我是不是让别人空等？ |

**销账规则**：收到回执 ⇒ 自动把 `ack` 填上；发一条"知悉"而没有对应派单 ⇒ 提示"可能对方本就没派单"。

> 没有台账的派单系统，等于**没有借条**：谁都记不清谁欠谁。

## 7. 分诊：没人认领的活怎么办

派单机制有个前提：**你知道该派给谁**。但现实里最常见的状态是"没人认领"。

规则：**看到"挂着待办却没归属 / 写了归属但对方不管 / 两边都说不是我的" ⇒ 不许当没看见。**

| 动作 | 谁做 |
|---|---|
| 判"该谁" → 有对口场景 ⇒ 派单（四件套） | 分诊方 |
| 谁都不合适 ⇒ 自己做，并在台账落一行 | 分诊方 |
| 拿不准 ⇒ **问机主一句**（别猜着办） | 分诊方 |

---

## 8. 失效模式（每条都真实发生过）

| 症状 | 根因 | 修法 |
|---|---|---|
| 派单发出去，对方毫无反应 | 只落盘没唤醒（把公告当派单） | 看投递回执：必须是"对方已接受"，不是"我写进文件了" |
| 双方互等，活停住 | 没有"未回执"状态 | 台账两张单 + 定期自查 |
| 两个 AI 来回客套 | 没有条数上限 | ≤3 条 + 知悉不回 + `【结束】` |
| 回执说"已修复"，实际没修 | 没要求证据 | 回执必须带"跑了什么、几条通过、差异集合" |
| 派单发出后没人再提 | 没有销账机制 | 收到回执自动销账；超时进"未回执" |
| 同一件活被派了两遍 | 派前没查"这事是不是已经在跑" | 派前查台账/在跑的活；撞车就只留一个写入者 |

---

## 9. 最小可用（3 个会话以内，只做这四条）

1. **判据写进习惯**：句子里有"请你改/做完回一句" ⇒ 走派单（真投递）；否则只落盘；
2. **派单四件套**：现象 / 照哪做 / 怎么验 / 回一句；
3. **回执必须投递 + 带证据**（结论 + 证据 + 落盘路径）；
4. **同一件事 ≤3 条，末行 `【结束】`**。

等你有 ≥3 个常驻会话、开始"忘了自己派过什么"了，再加**台账**（第 6 节）和**分诊**（第 7 节）。
