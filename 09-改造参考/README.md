# 09 · 改造参考 —— 对一款成熟 agent 产品做的逆向拆解

> **这是什么**：不是源码，是**分析笔记**。
> 拿一款已经做得很成熟的 AI agent 产品（下文代号 **Hermes**），从头拆一遍：
> 它怎么压缩上下文、怎么验证、怎么恢复失败、怎么做注入防御、本地模型怎么落地……
> 最后产出一份**「哪些值得抄、哪些不值得、抄要付什么代价」的改造清单**。
>
> ⚠ 产品名只用于**指代被观察的对象**；本目录不含它的任何源码或二进制，
> 全部是**观察记录 + 推断 + 自写参考实现**的结构化笔记。

---

## 为什么这种拆法值得学

大多数人研究竞品的方式是"看一遍、感慨一下、忘了"。
这套拆法的不同点是：**每一句结论都必须挂证据，每一条改造都写清代价**。

它的产出不是"我觉得它很强"，而是：

- **16 篇主线**：一个主题一篇（上下文压缩 / 验证 / 失败恢复 / 本地模型 / 注入防御 …）
- **17 篇证据**：每篇主线配一份证据（截图文案、字段表、行为复现步骤、边界实测）
- **一份改造清单**：逐条写「值不值得抄 / 抄的代价 / 抄完怎么验」
- **一份未解问题清单**：**没搞懂的明确写"没搞懂"**（这一页最能防自欺）

## 这套拆法的五步（可以直接照做）

```
① 侦察：先列"可能的机制面"（上下文 / 记忆 / 工具 / 验证 / 恢复 / 权限 / 成本 …）
        然后按"对你有用 + 能观察到"两个维度筛，别一头扎进细节
② 主线：一个机制一篇，固定三段式
        现象（用户能看到什么）→ 它怎么做的（推断 + 依据）→ 我们能怎么做（代价）
③ 证据：每篇主线必须有独立证据文件
        ⛔ 没有证据的主线 = 猜测，删掉或标"未验证"
④ 契约：把观察提炼成可执行的接口/字段/状态机（这一步把"看懂"变成"能实现"）
⑤ 参考实现：自己写一遍最小版（写不出来 = 没看懂）
──────────────────────────────────────────────────
最后两份：改造清单（抄不抄 + 代价 + 验收）· 未解问题（诚实列出没搞懂的）
```

**贯穿全程的一条纪律**：⛔ **别把"看起来"写成"它就是"**。
两栏区分：`观察到`（可复现）与 `推断`（可能错）。这一条决定了整份文档可信不可信。

## 改造清单长什么样（这才是产物）

每条只写四件事，**不写感受**：

| 字段 | 要求 |
|---|---|
| 抄什么 | 一句话说清那个机制 |
| 为什么值得 | 对我们的哪个具体痛点在起作用 |
| 代价 | 改哪个模块、要几天、会不会伤现有行为 |
| 怎么验 | 改完跑什么、看到什么才算成功 |

> 判据：**"抄完怎么证明它有用"这一栏写不出来的条目，就不该进清单。**
> 写不出来说明你只是觉得它"高级"。

## 怎么读（建议顺序）

1. [`Hermes/00-INDEX.md`](Hermes/00-INDEX.md) —— 先看它拆了哪些面（3 分钟）
2. [`Hermes/05-改造清单.md`](Hermes/05-改造清单.md) —— 直接看结论与代价（最有信息量的一篇）
3. 挑**跟你痛点最像**的那篇主线进 `02-主线/`，再翻它对应的 `06-证据/`
4. 最后看 [`Hermes/07-未解问题.md`](Hermes/07-未解问题.md) —— 看"作者也没搞懂什么"，比看成功经验更能校准判断

> ⚠ 主线里的数字、字段名、版本号都是**当时观察到的**，会过时；当"方法示例"读，别当规范。
