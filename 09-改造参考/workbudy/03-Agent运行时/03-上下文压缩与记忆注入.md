## 一、压缩是分层的，不是一刀切

【实证】bundle 里的相关常量与函数：

```
AUTO_COMPACT_WINDOW_MIN / AUTO_COMPACT_WINDOW_MAX   自动压缩的窗口区间
DEFAULT_MAX_CONSECUTIVE_COMPACT                     连续压缩上限（防死循环）
COMPACT_STRATEGY / runCompactStrategies()           多策略，择优
COMPACT_STARTED / COMPACT_ENDED / COMPACT_FAILED    压缩生命周期事件
POST_COMPACT                                        压缩完成后钩子
SESSION_META_COMPACTION_ID / _TRIGGER / _TYPE       压缩状态持久化到会话元数据
SESSION_META_PRE_MESSAGE_COMPACT_ENDED / _ERROR_MESSAGE
COMPACTION_HEADER / CONTEXT_COMPACTED_HEADER        压缩后的占位符文案
```

三层结构：

| 层 | 触发条件 | 做什么 |
|---|---|---|
| **microcompact** | 单条工具输出太大 | 截断/摘要这一条，不动历史 |
| **auto compact** | 上下文占用进入窗口区间 | 把中段历史压缩成摘要，保留头尾 |
| **session compaction** | 跨会话 | 把整个会话压缩成可复用的项目记忆 |

关键设计：**保留头尾，压中间**。系统提示 + 最早的用户意图 + 最近 N 轮对话不动，中间的工具调用链压成一段摘要。

## 二、"连续压缩上限"这个坑

`DEFAULT_MAX_CONSECUTIVE_COMPACT` 的存在说明一个问题：**压缩本身也消耗上下文**。

压缩 = 把 100 条消息喂给模型，让它吐 500 字摘要。这个过程要占满整个窗口。如果压缩完还是超，会再压一次，再超再压——无限循环，token 烧光。

所以要有：
1. 连续压缩次数上限，超了就强制截断（丢掉最早的，不做摘要）
2. 压缩失败要有降级路径（`COMPACT_FAILED` 事件 + `SESSION_META_COMPACT_CANCELLED`）

DSH 现在没有压缩，加的时候**第一版就要有这个熔断**，不要等出问题。

## 三、你自己的方案 vs 工程版

你在文案里定的规矩：主文件不超 25K、「当前交接」段覆盖写、压缩线到了引擎自己压。

这套是"文档级"的记忆管理，很好，但缺两块：

**缺 1：压缩后要能追溯**
WorkBuddy 压缩时会记 `compactionId` 和 `trigger`，压缩后的摘要带着原始 id。你只保留摘要，就丢失了"这段摘要是从哪几条消息来的"。

改法：摘要文件头部加一行元信息
```markdown
<!-- compact: id=a3f2, trigger=auto, from=seq:120-486, ts=2026-10-20T10:22 -->
```

**缺 2：压缩质量无法评估**
`prompt-trace-reporter.js` 干的就是这个——把每轮实际喂给模型的东西上报。没有它，你永远不知道压缩把什么重要信息压没了。

改法：每次压缩把"压缩前 token / 压缩后 token / 摘要"存一份到 `.dsh/compact-log/`，出问题时能翻。

## 四、记忆注入的时机（这点比内容更重要）

【实证】`workbuddy-memory-system.md` 里明确写了两件事：

1. **什么条件下才注入**：`{% if LocalSkillsMemoryEnabled %}` —— 开关控制，不是永远注入
2. **什么时候写**：完成实质工作后立刻写，且列出"什么算实质工作"

原文的关键段落：

```markdown
**When to write (MUST follow):** Immediately after completing substantive work, 
append a brief note to {{ WorkbuddyMemoryDir }}/YYYY-MM-DD.md using the Edit tool. 
Substantive work includes:
- Built or modified a website/application
- Fixed a bug
- Wrote or generated a report or document
- Completed code refactoring or architecture changes
- Chose a technical approach (framework, design pattern, etc.)
- User shared project conventions or preferences → also update MEMORY.md in place

Daily logs are append-only. Do NOT record transient information (search results, 
temporary paths, tool errors). Only persist what has lasting value across sessions.
```

三层记忆的分工：

| 层 | 位置 | 谁写 | 上限 |
|---|---|---|---|
| 云记忆 | 服务器生成 | 自动，本地改会被覆盖 | — |
| 用户级 | `~/.xxx/MEMORY.md` | 显式要求才写 | 4000 字符/会话 |
| 工作区 | `<project>/.xxx/memory/` | 每完成实质工作就写 | 3000 字符/会话 |

**注意"上限按会话计"这个设计**——它不是文件大小限制，是"这个会话最多能往这个文件里写多少字"。防止模型把记忆当垃圾场。

## 五、DSH 的落地建议

按你现有的 md 体系，改动最小：

```
.dsh/
├── project.md            项目宪法（你的主文件，25K 红线不变）
├── memory/
│   ├── MEMORY.md         长期结论（限 3K/会话）
│   └── 2026-10-20.md     每日日志（append-only）
└── compact-log/          压缩留痕（新加）
```

三步走：

1. **加熔断**：连续压缩 > 2 次就放弃摘要，直接丢弃最早 30% 历史并留一行 `[已丢弃 N 条，未摘要]`
2. **加留痕**：每次压缩存元信息 + 摘要，供事后追责
3. **加开关**：记忆注入做成可关的。你现在的方案是永远注入，长会话里这是一笔固定开销
