# 工具系统与三种权限模式

## 一、权限模式是枚举，不是布尔

【实证】`parsePermissionMode()` 的完整映射表：

```js
{
  default:           ZC.Default,
  acceptEdits:       ZC.AcceptEdits,
  bypassPermissions: ZC.BypassPermissions,
  plan:              ZC.Plan,
  dontAsk:           ZC.DontAsk,
  auto:              ZC.Auto,
  ignore:            ZC.Ignore,
}
```

DSH 现在只有"完全权限"一个开关，等价于永远停在 `bypassPermissions`。**这是最危险的位置**——它把"模型判断"和"用户授权"两件事合并成了一个。

这七个值可以归成三类：

| 类 | 值 | 含义 |
|---|---|---|
| 交互式确认 | `default` | 敏感操作弹窗问 |
| 自动化授权 | `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions` | 分级放手 |
| 只读/隔离 | `plan` / `ignore` | 不许动 |

## 二、模式怎么真正约束工具（关键）

**不是提示词说"别改"，是工具集里没有"改"。**

注意 `Defer(Xxx)` 这个写法：**同一个工具，不同模式下的加载策略不同**。有的模式里工具直接可用，有的模式里只能"现查现用"（进 `ToolSearch` / `DeferExecuteTool` 通道）。

对比 Ask 模式（`ask/fragments/mode-behavior.md` 全文）：

```markdown
<ask_mode_behavior>
- Your goal is to help the user understand the problem and create a detailed plan if needed.
- The USER is only asking questions, not requesting edits.
- First explain the underlying logic, principles, or relevant details.
- After gathering enough context, create a clear plan if the user needs one. Use Mermaid diagrams when helpful.
- Once the plan is confirmed, ask the USER to switch to Agent mode to implement it.
</ask_mode_behavior>

<system_reminder>
The user is in ask mode; only read-only tools are available.
If write/edit/terminal tools are required, let them know they should switch to Agent mode.
</system_reminder>
```

**两层保险**：工具集层面拿不到写工具 + 提示词层面明确告诉它"为什么拿不到、该怎么办"。只做前者，模型会反复尝试调用不存在的工具然后卡住；只做后者，等于没做。

## 三、工具延迟加载（DSH 最该抄的一条）

【实证】工具分两类：
- **直连工具**：schema 常驻初始上下文
- **延迟工具**：只暴露一个名字，schema 要用时现查（`ToolSearch` → `DeferExecuteTool`）

MCP 侧对应 `.mcp.json` 里的 `defer_loading` 字段：

```json
{
  "mcpServers": {
    "miora": { "type": "stdio", "command": "node", "defer_loading": false }
  }
}
```

代价与收益：
- 一个工具的 schema 平均 300–800 token。50 个工具全量注入 = 1.5–4 万 token，**每轮都付**
- 延迟加载后，常驻成本 ≈ 每个工具 10–20 token（只有名字和一句话）
- 代价：模型要多一次往返（先搜再调）

**【实证】踩坑记录**（`high-credit-gate.cjs` 注释原文）：
> 若插件走 defer 加载，工具调用会先经 `DeferExecuteTool`。bypass 模式下它的前置 `checkPermission` 返回 allow 并直接短路返回「无需审批」，本 hook 压根不会被执行。计费工具的插件必须在 `.mcp.json` 显式写 `defer_loading: false`（全局默认是 true）。

这条极其重要：**延迟加载会绕过 PreToolUse Hook**。你如果给 DSH 加审批闸门，被闸门保护的工具绝对不能走延迟通道。

## 四、工具调用的完整生命周期

【实证】从 `executeToolWithHooks` 与 MCP 调用路径反推：

```
模型发出 tool_call
  ├─ 1. 死循环检查   toolCallLoopGuard.checkBeforeExecute(session, name, call)
  │      → 返回 "stop" 则抛异常终止
  ├─ 2. PreToolUse Hook
  │      ToolHookManager.executePreToolUseHooks(name, input, session, path, cwd, callId)
  │      → { allowed, permissionDecision, message, modifiedInput, preventContinuation }
  │      → 结果按 callId 缓存进 session.preToolUseHookResults，判过不重复判
  ├─ 3. 参数改写      hookResult.modifiedInput 覆盖原 input
  ├─ 4. 权限判定      needsApproval → 弹窗 / 自动通过
  ├─ 5. 出站授权      authorizeMcpEgress(input, session, ..., `mcp:${server}/${tool}`)
  ├─ 6. 最终动作授权  authorizeMcpFinalAction({ entry, input, preResult })
  │      ← 这一层能看到 hook 改写后的参数，防"hook 放行原参数、模型换参数再调"
  ├─ 7. 真正执行
  └─ 8. PostToolUse Hook（成功/失败两条：PostToolUse / PostToolUseFailure）
```

**第 6 步是精髓**。如果只做一次授权，模型可以在 hook 通过之后换参数。DSH 如果要做 SSH 拦截，必须校验**最终执行的那条命令**，而不是模型第一次提交的那条。

## 五、给 DSH 的最小改造方案

```js
// 1. 模式定义搬成配置文件，别写在代码里
// modes/readonly.json
{ "name": "readonly", "tools": ["read_file","grep","glob","sql_query","ssh_exec:readonly"] }

// 2. 工具注册表按模式过滤
function getToolsForMode(mode) {
  const allowed = loadMode(mode).tools;
  return registry.filter(t => allowed.includes(t.name) || allowed.includes(t.name+':*'));
}

// 3. 三种模式，够用
//    readonly  — 生产只读，默认用它
//    plan      — 能读能查，产出方案，禁止写
//    execute   — 全开，但要过审批闸门

// 4. UI 上把模式做成显眼的三段开关，不是隐藏下拉
```

**别做**：七种模式全抄。`acceptEdits` / `dontAsk` / `auto` / `ignore` 这四个是为了覆盖各种产品形态（IDE 内联、CI、后台任务）才存在的，DSH 只有桌面单机一种形态，三档足够。
