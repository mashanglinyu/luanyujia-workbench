# 多智能体与工作流

## 一、三种并行粒度

【实证】从工具清单与运行时类名反推，WorkBuddy 的并行是三档，不是一档：

| 档 | 机制 | 适用 |
|---|---|---|
| **子代理** | `Agent({prompt, description, name, run_in_background})` | 一次性任务，结果回主会话 |
| **团队** | `TeamCreate` + `CreateColleague` + `SendMessage` + `SpeakInChannel` | 多个角色长期协作，需互通 |
| **工作流** | `cli/builtin/workflows/*.workflow.js` | 固定的多阶段流水线 |

DSH 现在一档都没有。**先做第一档就够**（很多场景其实只需要"派出去、等结果"）。

## 二、子代理的调用契约

【实证】从 PTC/Code Mode 提示词片段里提取的用法（原文）：

```js
// 并行派发
await Promise.all(agents.map(a => Agent({
  description: a.description,
  prompt: a.prompt,
  name: a.name,
  run_in_background: true
})))

// 注意：命名 Agent() 会自动建团队，不需要先 TeamCreate
// 失败的 spawn 会 throw，所以不要写 results.map(r => r.taskId ?? r.id)
// 也不要写 Promise.all(...).catch ? ... : ...
// 成功后 r.taskId 带回来
```

三个细节，都是踩过坑才会写进提示词的：

1. **`name` 有副作用**：命名即入团队。不想要团队就别传 `name`
2. **`run_in_background: true` 立刻返回 `taskId`**，结果要 `TaskOutput` 去取
3. **spawn 失败是抛异常不是返 null**，所以不能用 `?? ` 兜底——那句话是写给模型看的防呆提示

配套工具：`TaskStop`（停）、`TaskOutput`（取输出，`block:true` 等完成 / `block:false` 看进度）。

## 三、工作流（最值得看的一个文件）

`cli/builtin/workflows/deep-research.workflow.js` 是完全明文的，23KB，一个完整的多 Agent 流水线。结构：

```js
export const meta = {
  name: 'deep-research',
  description: '...',
  whenToUse: '什么时候该用这个工作流（含反例：问题不够具体要先追问）',
  phases: [
    { title:'Scope',  detail:'Decompose question into 5 search angles' },
    { title:'Search', detail:'5 parallel WebSearch agents, one per angle' },
    { title:'Fetch',  detail:'URL-dedup, fetch top 15, extract falsifiable claims' },
    { title:'Verify', detail:'3-vote adversarial verification (need 2/3 refutes to kill)' },
    { title:'Synthesize', detail:'Merge dupes, rank by confidence, cite sources' },
  ],
}
```

**这个 `meta` 结构本身就是可抄的**：`name` / `description` / `whenToUse` / `phases`。它让"工作流"变成一个模型能自己判断该不该用的东西，而不只是一段代码。

里面几个真正实用的设计：

**1. 对抗式验证（3 票制）**
每条论断派 3 个独立 agent 去证伪，2/3 判定为假才杀掉。这是抑制幻觉的有效手段，成本可控。

**2. 降级不抛弃**
```js
if (!report) {
  // Synthesis skipped/errored — salvage the verified claims raw rather
  // than throwing on report.findings and discarding the whole run.
  return formatReport({ ... findings: confirmed.map(...), summary: "Synthesis step was skipped or failed — returning N verified claims unmerged." })
}
```
最后一步失败时，**返回中间产物**而不是抛异常。跑了 20 个 agent 结果一步失败全丢，是最蠢的设计。

**3. 手工 JSON 校验代替 schema**（这条对你特别重要）

原文注释：
> Model compatibility: no `schema` param in agent() — **deepseek-chat doesn't support reasoning_effort + structured output simultaneously**. Instead, models output JSON text and we parse/validate manually.

也就是说：**DeepSeek 不能同时用推理模式和结构化输出**。WorkBuddy 的应对是让模型输出 JSON 文本，然后自己 `extractJSON`（依次尝试 ` ```json ` 代码块 / 普通代码块 / 裸 `{...}`）+ `validateJSON`。

DSH 跑的就是 DeepSeek，这条等于别人替你踩过的坑。直接抄那 60 行 helper。

## 四、DSH 的最小落地方案

### 4.1 只做一个工具：`spawn_agent`

```js
// 不搞团队、不搞 channel，就一个
{
  name: 'spawn_agent',
  params: {
    task: 'string',            // 要干什么
    role: 'string?',           // 可选人设
    tools: 'string[]?',        // 限定它能用的工具子集 ← 关键
    background: 'boolean?',    // 默认 true
  }
}
```

`tools` 参数是关键：子代理默认应该是**只读**的。派 5 个 agent 出去都带写权限，等于把事故概率乘 5。

### 4.2 目录结构

```
.dsh/
├── agents/
│   ├── researcher.md     角色定义（就是一段提示词）
│   └── verifier.md
└── workflows/
    └── oa-health-check.workflow.js   你的"每周体检"可以直接做成工作流
```

### 4.3 直接能用的场景

你的业务里最适合改成工作流的：**每周日 8 类体检**。
现在是人（或一个会话）顺序跑 8 项。改成工作流：8 个只读 agent 并行跑，1 个汇总 agent 出报告。耗时从 8×t 变成 t，而且单项失败不影响整体。

```
phases: [
  { title:'排查', detail:'8 项检查并行，每项一个只读 agent' },
  { title:'归因', detail:'对失败项做二次确认，排除瞬时抖动' },
  { title:'报告', detail:'汇总成体检报告 + 与上周对比' },
]
```
