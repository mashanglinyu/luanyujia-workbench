# 压缩与注入的完整机制（细查报告）

> 这份是对 `03-上下文压缩与记忆注入.md` 的**实证升级**。
> 上一份是摸到了结构，这份挖到了**具体参数、判定顺序、以及"压缩其实不用调模型"这件事**。
> 所有数字都是从 bundle 里直接读出来的，不是估的。

---

## 零、一句话结论

**它的上下文管理不是"快满了让模型写摘要"，是三级降级流水线：**

```
① microcompact（纯代码，按时间/大小清工具结果）   ← 0 token
      ↓ 还不够
② engineering compact（纯代码，把历史重写成紧凑剧本） ← 0 token
      ↓ 还不够（剩余 > 窗口 15%）
③ LLM summary（真的调模型写摘要）                  ← 唯一花 token 的一步
```

**前两级完全不花钱、不产生幻觉。** 你现在缺的就是前两级——直接把"压缩"等同于"让模型总结"，所以又贵又不稳。

---

## 一、三级压缩，逐级看

### 第 0 级：microcompact —— 按时间清垃圾

【实证】`performMicrocompact()` @7293274

```
清理对象：function_call_result 类型，且工具名在
  {Read, Bash, Grep, Glob, WebFetch, WebSearch, Edit, MultiEdit, Write, REPL}

默认策略（无参）：清掉 1 小时前的所有工具结果
  cutoff = Date.now() - 3600000
  替换文案 = "[Old tool result content cleared by microcompact]"

激进策略（传 keepRecent）：
  保留最近 N 条，其余截断到 maxCharsPerResult = 1500 字符
  截断文案 = "[... content truncated by microcompact to fit context limit]"
```

**关键洞察**：它区分了"工具结果"和"对话内容"。工具结果是可以按时间丢的——一小时前的 `ls` 输出对现在没有任何价值。但对话不能按时间丢。

你现在的做法是把整段历史一起压，等于把有价值的判断和没价值的日志一起埋了。

### 第 1 级：engineering compact —— 代码重写历史

【实证】`HistoryEngineeringCompactor.compact()` @7759837

这一步**不调用模型**。它把历史逐条改写成一种紧凑剧本格式：

```
丢弃的类型（ac 集合）：
  function_call_result  reasoning  custom-title  topic  ai-title
  summary  file-history-snapshot

用户消息  → <previous_user_message>
              <user_query>{正文}</user_query>
            </previous_user_message>

助手消息  → <previous_assistant_message>{正文}</previous_assistant_message>

工具调用  → <previous_tool_call>
              Tool: {工具名}
              Arguments: {参数}
              <result><omitted /></result>
            </previous_tool_call>
```

**三个魔鬼细节**：

1. **工具结果统一写成 `<omitted />`**。注意：不是"丢掉这一轮"，是保留"调了什么工具、传了什么参数"，只把返回结果抹掉。这样模型还知道"我查过表结构"，只是不再看到那 3000 行输出。
2. **参数脱敏**（`processToolArguments`）：
   ```
   content / widget_code / new_string  →  "<omitted>"
   ```
   这三个是"大块正文"字段（写文件的内容、生成的 HTML、编辑的新文本）。不脱敏的话，一次写文件的调用就能把摘要撑爆。
3. **token 估算用字符数 / 4**（`ad = 4`）。粗糙但够用，不需要 tokenizer。

**输出信封**：

```
<cb_summary>
Summary of the conversation so far:
The conversation is between an AI agent and a user.
Use this to get up to speed, and continue helping the user as the AI agent.
Some contents may be omitted, indicated by "<omitted />".

{压缩后的正文}
</cb_summary>
```

### 第 2 级：LLM summary —— 到这一步才花钱

只有在第 1 级压完仍然不够时才走。判据是**充分性比率**：

```
getEngineeringCompactSufficiencyRatio()
  默认 0.15（可用环境变量 CODEBUDDY_ENGINEERING_COMPACT_SUFFICIENCY_PCT 覆盖）
```

意思是：**压完如果还占窗口 15% 以上，认为工程压缩不够充分，升级到 LLM 摘要。** 压到 15% 以下就收工。

这个阈值很讲究——15% 是个"摘要大概也就能压到这么多"的经验值。定得比它宽就是白压，定得比它窄就会多做无用的模型调用。

## 二、什么时候触发：三个时机

【实证】`CompactType` 枚举 @7262836

| 触发类型 | 值 | 时机 |
|---|---|---|
| 手动 | `user-command` | 用户输入 `/compact` |
| **发消息前** | `pre-message-auto` | **每轮对话开始前检查** |
| 紧急 | `emergency-auto` | 真的快满了 |

**`pre-message-auto` 是最容易被忽略的一层**：它不是等上下文爆了再压，而是每轮发消息前先看一眼，超阈值就压。好处是压缩发生在空闲时刻，不打断正在进行的推理。

配套阈值（`tR = .7` / `tP = .5`）：

```
CODEBUDDY_PRE_MESSAGE_COMPACT_PCT   默认 50%   ← 到半窗就预备压缩
CODEBUDDY_AUTOCOMPACT_PCT_OVERRIDE  默认 70%   ← 到七成就自动压缩
```

窗口本身：

```
默认 200,000 token（tI = 2e5）
下限 100,000（tO = 1e5）
上限 1,000,000（tx = 1e6）
可用 CODEBUDDY_AUTO_COMPACT_WINDOW 覆盖，支持 "auto" / "400k" / "1m" 写法
```

**50% 就开始准备**这件事值得你抄。等 95% 才动手，你会连压缩本身所需的空间都不够——压缩也是要喂上下文的。

## 三、压缩时的"减法"清单（这些比加法重要）

在把历史交给压缩器之前，它先做了一轮清理：

```js
createFilteredCopyForCompaction(messages)
  ├─ filterHiddenSystemRemindersForCompaction()  剥掉所有 <system-reminder>
  ├─ stripUserQueryTagsFromMessages()           剥掉 <user_query> 包装
  └─ stripImagesForCompaction()                 所有图片 → "[image]"
```

**为什么要剥 system-reminder？** 因为那些是运行时注入的（记忆、模式提醒、todo 提醒），每一轮都会重新注入。把它们写进摘要，等于把临时状态固化成永久记忆——下次注入时就和摘要里的旧版本打架了。

这条对你有直接价值：**你的"当前交接"里如果把注入内容也写进去，就会自我污染。**

## 四、压缩后的两件事：指针与继续

### 4.1 留指针，不留全量

【实证】`wrapSummaryWithContext()` @7240929

```
This session is being continued from a previous conversation that ran out of
context. The summary below covers the earlier portion of the conversation.

Summary:
{摘要正文}

If you need specific details from before compaction (like exact code snippets,
error messages, or content you generated), read the full transcript at:
{transcript 文件路径}
```

最后那句是精髓：**摘要负责"知道发生过什么"，指针负责"需要细节时去哪找"**。两者配合，摘要才能放心写短。

你现在"当前交接覆盖写会丢细节"的根本原因就在这里——你只有摘要，没有指针。摘要写短了就丢信息，写长了又占地方，怎么都不对。

### 4.2 压缩完自动发"请继续"

【实证】`sendContinueMessage()` @7763497

压缩完成后不是干等着，而是自动追加一条继续消息：

- 子 agent：`Please continue based on the summarized context above. Your original task was: "{originalUserIntent}"`
- 主 agent：直接用摘要继续

**为什么需要这条**：压缩会中断当前 run（`abortCurrentStreamAndWait`），必须显式恢复，否则会话卡在 COMPACTING 状态。

顺带还有个真实 bug 的修复痕迹值得记：

> `skipContinue=true but a run was aborted during compaction; forcing continue run to avoid deadlock (issue #91416)`

翻译：配置说"压完不用继续"，但压缩过程本身中断了一个正在跑的 run，这时候不继续就死锁了。**所以"跳过继续"这个优化必须让位于"不能死锁"**。你实现时一定会遇到这个坑。

## 五、失败处理：压缩也会失败

【实证】相关符号

```
CompactSummaryNotFoundError       摘要输出格式不对，直接抛错
SESSION_META_COMPACT_CANCELLED    被取消
SESSION_META_PRE_MESSAGE_COMPACT_ERROR_MESSAGE   压前压缩的错误
truncateAndCompactAsFallback(history, ap=5)      兜底
```

**`truncateAndCompactAsFallback` 是最后一道防线**：不摘要了，直接砍掉历史，只保留最近 **5 轮**（`ap = 5`）。

压缩 agent 自己的 `maxTokens` 默认 **24000**（`au = 24e3`），继承默认 agent 的其他模型设置。

## 六、第二个发现：系统提示不是一篇，是每轮注入

这是这次细查里**比压缩更重要的发现**。

### 6.1 记忆根本不进系统提示

【实证】`SystemReminderAgentRunInterceptor` @3124147

```js
if (this.shouldInjectSystemReminder(session)) {
  const template = promptManager.get("system-reminder-md");
  const rendered = promptManager.render(template, {
    userMemory,      // scope: USER
    projectMemory,   // scope: PROJECT
    localMemory      // scope: PROJECT_LOCAL
  });
  addSystemReminder(input, rendered, "first");   // ← 插到用户消息的第一位
}
```

三层作用域 + 每轮渲染 + 插到用户消息的**首位**。

同一条流水线上还有这些独立 reminder，各自决定插不插、插哪：

```
rules（记忆/规则）        → position: "first"
plan-mode                 → position: "last"
delegate-mode             → position: "last"
ide-selection             → position: "last"
hook 注入的上下文          → 由 hook 决定
```

### 6.2 为什么这么做

如果把记忆拼进系统提示，会发生两件坏事：

1. **prompt cache 失效**。系统提示一改，整个前缀缓存全废。
2. **记忆一更新就要重建整篇提示**。而记忆是每轮都可能变的。

改成"系统提示是稳定骨架 + 记忆每轮注入到消息里"，两个问题同时消失。代价是每轮多几十 token，换来的是缓存稳定。

### 6.3 系统提示本身怎么拼

【实证】`ProductProvider` 分层

```
provider.priority = OPTIONS / AGENT_MODEL_RESOLVER+100 / ...
provider.provide() 返回一个 patch
最终 mergeStrategy: SmartMerge
```

每个 provider 只负责自己那一片（CLI 选项、agent 定义、模型同步……），系统按优先级合并。不是"一个函数拼出整篇"，是"多个来源各交一份补丁"。

## 七、顺带挖到的：REPL 沙箱模式

【实证】@1241895 附近

有一个模式把所有工具变成沙箱里的 async 全局函数，模型写 JS 程序来调用：

```
REPL is the only tool you can call directly; inside it Bash, Edit, Skill,
and coordinator tools exist.
Read, Write, Glob, Grep, and MCP are unavailable both outside and inside REPL.
Call a catalog tool as `await <Name>({ ... })`
```

**意义**：当任务需要"连续调 20 次工具"，逐次往返的协议开销远大于让模型写一个循环。REPL 模式把 N 次协议往返变成 1 次。同时它也是最强的权限收敛——REPL 里根本没有 Write 工具。

这个对你不是刚需，但记一下：**工具集可以按"调用形态"重组，不只是按权限**。

## 八、你的做法 vs 它的做法

| 维度 | 你现在 | 它的做法 | 差距性质 |
|---|---|---|---|
| 压缩触发 | 到线了才压 | 50% 预备、70% 自动 | 时机 |
| 压缩手段 | 单一（摘要） | 三级降级，前两级 0 token | **架构** |
| 压缩单位 | 整段历史 | 工具结果单独清、历史单独重写 | 粒度 |
| 摘要格式 | 自由文本 | 结构化信封 + 格式校验 + 失败抛错 | 契约 |
| 丢失细节 | 只能接受 | 留 transcript 指针 | **可恢复性** |
| 记忆位置 | 拼进主 md / 系统提示 | 每轮注入到消息首位 | 缓存与稳定 |
| 记忆分层 | 一份 | USER / PROJECT / PROJECT_LOCAL | 作用域 |
| 失败处理 | 无 | 兜底砍到最近 5 轮 | 鲁棒性 |

标粗的两处是架构级差距，其他都是实现级。

## 九、DSH 的最小实现（按这个顺序写）

### 第 1 步：先做 microcompact，不做摘要（半天）

```python
def microcompact(history, keep_recent=None, max_chars=1500):
    """0 token 成本。这一档能解决你 80% 的长会话问题。"""
    TOOLS = {"read","bash","grep","glob","fetch","search","edit","write","ssh","sql"}

    if keep_recent is None:
        cutoff = now() - 3600          # 1 小时
        for item in history:
            if item.type == "tool_result" and item.tool in TOOLS:
                if item.ts < cutoff:
                    item.output = "[Old tool result content cleared by microcompact]"
    else:
        idxs = [i for i,x in enumerate(history)
                if x.type=="tool_result" and x.tool in TOOLS]
        for n, i in enumerate(idxs):
            if n < len(idxs) - keep_recent:
                history[i].output = "[... content truncated ...]"
            else:
                history[i].output = history[i].output[:max_chars]
```

**验收**：跑一次长会话，看 token 曲线。如果只是在"到线"时才降，说明没生效。

### 第 2 步：再做工程压缩（一天）

```python
DROP_TYPES = {"reasoning","topic","ai-title","summary","snapshot","tool_result"}
BULK_ARGS  = {"content","new_string","widget_code"}   # 脱敏

def engineering_compact(history):
    out = []
    for it in history:
        if it.type in DROP_TYPES: continue
        if it.type == "tool_call":
            args = {k:("<omitted>" if k in BULK_ARGS else v) for k,v in it.args.items()}
            out.append(f"<previous_tool_call>\nTool: {it.name}\n"
                       f"Arguments: {json.dumps(args)}\n"
                       f"<result><omitted /></result>\n</previous_tool_call>")
        elif it.role == "user":
            out.append(f"<previous_user_message>\n<user_query>\n{it.text}\n"
                       f"</user_query>\n</previous_user_message>")
        elif it.role == "assistant":
            out.append(f"<previous_assistant_message>{it.text}"
                       f"</previous_assistant_message>")
    body = "\n\n".join(out)
    return f"<cb_summary>\n{HEADER}\n\n{body}\n</cb_summary>"

def estimate_tokens(s): return len(s) // 4
```

**验收**：不调模型，历史 token 降 60% 以上，且模型还能说出"我改过哪个文件"。

### 第 3 步：最后才做 LLM 摘要（两天）

```python
def maybe_compact(history, window=200_000):
    used = estimate_tokens(render(history))
    if used < window * 0.5: return history

    h2 = microcompact(history)
    if estimate_tokens(render(h2)) < window * 0.15: return h2

    h3 = engineering_compact(h2)
    if estimate_tokens(h3) < window * 0.15: return [h3]

    summary = llm_summarize(h3)          # 只有走到这里才花钱
    return [wrap_with_context(summary, transcript_path=session_file)]
```

**注意顺序**：先清后压再摘要。反了就是白花钱。

### 第 4 步：改成每轮注入（一天）

把现在拼进主 md / 系统提示的那些东西（模式提醒、todo、记忆、环境信息）拆出来，改成每轮渲染成 `<system-reminder data-role="...">` 插到用户消息里。

**验收**：改一次记忆文件，不需要重建系统提示；prompt cache 命中率上升。

## 十、还有一个避不开的坑

压缩期间会中断正在跑的 run。中断之后必须显式发一条 continue，否则会话卡死在 COMPACTING。而"跳过 continue"这个优化，在"压缩过程中刚好中断了 run"的情况下会导致死锁——它的处理是**强制继续**（宁可多发一条继续消息，不能死锁）。

实现顺序上，先把 continue 做对，再考虑优化。
