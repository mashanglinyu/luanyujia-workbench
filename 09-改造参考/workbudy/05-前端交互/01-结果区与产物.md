# 结果区与产物

> DSH 最大的结构性缺口：产出散落在终端日志和文件树里，没有"交付物"这个概念。

## 一、WorkBuddy 的做法：把"展示结果"变成一个工具

【实证】`craft/fragments/result-presentation.md` 全文：

```markdown
<result_presentation>
After you have completed the main execution steps of the current task and produced 
a concrete result, you MUST present the result to the user for review. 
This is a mandatory final step — do NOT skip it.

final result example: HTML, final report, pptx, video etc.

Rules:
1. **Use present_files for every result**: Call present_files with the result files. 
   It is the single entry point — for HTML files it automatically opens a live preview 
   panel AND lists them as artifact cards; for images, reports, pptx, video, code files, 
   etc. it shows them as artifact cards. You can pass multiple file paths in a single call.
2. You can also pass an http/https URL to present_files (e.g. a localhost dev server 
   you started) to open it in the built-in browser preview panel. For localhost URLs, 
   start the server first with the Bash tool.
3. Call present_files ONLY when you have actually finished the task and the result is 
   ready to view. Do NOT call it for partial or expected-future results.
4. Only present newly generated deliverable files — do NOT present files you merely 
   read or modified in-place.
5. This tool is for result presentation only — it does not block or alter your normal 
   reply. You should still provide a concise summary in your text response.
6. NEVER forget this step. Every completed task that produces a viewable result MUST 
   end with a present_files call.
</result_presentation>
```

四个设计决定，每个都有理由：

**1. 是一个工具，不是 UI 自动行为**
模型自己决定"这些东西该给你看"。UI 自动扫目录会把临时文件也列出来，模型判断更准。

**2. 单一入口**
一个 `present_files` 处理所有类型：HTML → 实时预览面板；图片/报告/PPT/视频/代码 → 产物卡片。而不是给每种类型一个工具。

**3. 必须放最后一步**
"your FINAL tool call in that turn MUST be present_files"。原因：产物列表要在回复生成之前定下来，否则回复里说的和列表对不上。

**4. 明确排除项**
"Only present newly generated deliverable files — do NOT present files you merely read or modified in-place."
只读的文件不进产物列表，否则列表很快被污染。

## 二、右栏的双 Tab 结构

【实证】`00-INDEX` 时看到的界面说明（官方文档）：

> **结果区** 右侧面板，提供**概览**与**产物**两类内容，可在同一区域切换查看。

- **概览**：这次任务的摘要（做了什么、结论是什么）
- **产物**：文件卡片列表，点击预览

而你截图里右栏是 `本地文件` 树（临时 / git / 备份 / 打包 / 归档产品 / 子账号 / 数据库备份 / 新闻资讯 / 幼儿教育项目 / 任务清单 / 素材 / 插件 / 照片素材 / 未来方案）。

**这两个是不同的东西**：
- 文件树回答"我的东西在哪"
- 产物区回答"这次任务给了我什么"

两个都要，但不能互相替代。建议做成 Tab 切换，默认停在产物（任务刚结束时人最关心的是"给我什么了"）。

## 三、产物卡片该显示什么

参考 WorkBuddy 的卡片信息密度，最少的必要字段：

```
┌─────────────────────────────────────┐
│ [图标] 体检报告-2026-10-20.md        │
│        12.4 KB · 2 分钟前 · 新增     │
│        ─────────────────────────    │
│        本周 CPU 峰值 78%，磁盘 61%…  │
│                    [预览] [打开目录] │
└─────────────────────────────────────┘
```

- 类型图标（一眼分辨 md/html/png/xlsx）
- 大小 + 相对时间（"2 分钟前"比"10:22:31"有用）
- 变更性质（新增 / 修改 / 替换）
- 首行内容摘要（比文件名信息量大）
- 两个动作：预览、打开所在目录

## 四、DSH 的最小实现

### 4.1 数据结构

```sql
CREATE TABLE artifacts (
  id          INTEGER PRIMARY KEY,
  task_id     TEXT NOT NULL,
  path        TEXT NOT NULL,
  kind        TEXT,           -- md/html/image/table/pdf/code
  size        INTEGER,
  sha1        TEXT,           -- 去重用
  change_type TEXT,           -- added / modified
  created_at  INTEGER,
  preview     TEXT            -- 首 200 字，卡片展示用
);
```

### 4.2 采集时机

**不要实时 watch 文件系统**（噪音太大、性能差）。用两个时机：

1. **任务结束时**：比对任务开始时的目录快照，diff 出新增/修改的文件
2. **模型显式调用**：给模型一个 `present_artifact(path)` 工具，它主动声明"这个重要"

第二个是关键——否则 AI 生成在 `/tmp` 的东西、或者改了但内容不重要的东西都会进列表。

### 4.3 清扫

【实证】WorkBuddy 有独立的 `archive-artifact-sweep.js`（37KB）。产物目录会无限膨胀，必须有清扫策略。

DSH 建议：产物 **90 天**后归档到 `_archive/`，卡片列表默认只显示最近 30 天，加"查看全部"。

## 五、你的产品里有个特殊优势

WorkBuddy 的产物终点是"用户自己看"。**你的产物终点是家长端和教师端**。

这意味着结果区可以多做一步：产物卡片上加一个 `→ 推送到家长端` 的按钮，把 AI 生成的班级报告/活动方案直接变成家长端的一个临时页面。

这条链 WorkBuddy 帮不上你，但它是你最该做的差异化。
