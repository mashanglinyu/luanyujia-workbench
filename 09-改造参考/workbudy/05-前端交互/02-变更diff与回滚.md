# 变更 diff 与回滚

> 本节**没有现成代码可抄**——WorkBuddy 这块在渲染层（打包后的 asar 里），没有明文。
> 下面是从它的行为特征 + 同类工具（Claude Code / Cline）的通行做法反推的**设计建议**，标【推断】。
> 但运维场景它是刚需：AI 改了生产环境的文件，你必须能看见改了哪几行、能退回去。

## 一、为什么必须做

你现在的能力矩阵：

| 阶段 | 你有什么 |
|---|---|
| 事前 | 无（SSH 命令直接执行） |
| 事中 | 操作日志（10 张）、SQL 审计 |
| 事后 | 有日志，但**没有内容级 diff，没有回滚** |

所以你现在的实际状态是：**AI 一旦改错，你只能靠记忆和备份手工恢复**。

这不是"体验优化"，是"敢不敢放手"的问题。没有它，你永远只能让 AI 干只读的活。

## 二、三层防护，从轻到重

### 第 1 层：变更登记（必须做，成本最低）

每次写操作前记录一条元信息，不存内容：

```sql
CREATE TABLE file_changes (
  id          INTEGER PRIMARY KEY,
  task_id     TEXT,
  tool_call_id TEXT,
  path        TEXT,
  op          TEXT,      -- write / edit / delete
  bytes_before INTEGER,
  bytes_after  INTEGER,
  ts          INTEGER
);
```

**只做这一层的作用**：你至少能回答"这次任务动了哪些文件"。0.5 天工作量。

### 第 2 层：内容快照（建议做）

写之前把原文件复制一份：

```
.dsh/snapshots/
└── <task_id>/
    └── <相对路径>.r<N>
```

关键设计：
- **按 task_id 分目录**，一个任务的所有快照在一起，回滚时能整批退
- **`r<N>` 递增**，同一文件被改多次都留
- **存压缩后的**（gzip），文本文件压缩率通常 80%+，10GB 磁盘够存几万个版本
- **超过 N 天的快照自动清理**（保留"最后一次"，中间版本可丢）

### 第 3 层：可视化 diff + 一键回滚（体验层）

```
右栏 → 变更 Tab
┌──────────────────────────────────────────────┐
│ 本次任务修改 3 个文件                         │
│                                              │
│ M  /www/wwwroot/oa/config/database.php       │
│    +12 −3        [查看 diff] [回滚]           │
│ M  /www/wwwroot/oa/app/Http/Controllers/...  │
│    +45 −8       [查看 diff] [回滚]           │
│ A  /www/wwwroot/oa/storage/logs/error.log    │
│    +320         [查看 diff] [删除]           │
└──────────────────────────────────────────────┘
```

diff 渲染用统一 diff（`diff -u`），行内高亮增删。别自己写 diff 算法，用现成库。

## 三、三个技术坑

### 坑 1：不要用 git 做这件事

直觉是"工作目录本来就是代码库，用 git stash / git diff 多方便"。但有三个问题：

1. **会污染用户仓库**：AI 的临时改动进 `git status`，用户下次 commit 会带进去
2. **工作目录可能不是 git 仓库**（`/www/wwwroot` 下很常见）
3. **`.gitignore` 会让重要文件不被追踪**（配置文件、密钥——恰恰是最危险的）

用独立的 `.dsh/snapshots/`，跟版本控制解耦。

### 坑 2：二进制文件不要存快照

图片、压缩包、数据库文件——存了会撑爆磁盘，而且 diff 没意义。

处理方式：
- 大小 > 1MB 且非文本 → 只登记元信息（路径、大小、mtime），不做快照
- 回滚时提示"该文件未存快照，需从备份恢复"

判断是否文本：读前 8KB，如果 `\0` 字节占比 > 1% 就当二进制。

### 坑 3：远程文件怎么办

你的场景里大量是 SSH 到 `47.108.x.x` 改文件。本地快照存不了远程内容。

方案：**改远程文件前先 `cat` 回来存本地**。

```bash
ssh user@host "test -f /path/x && cat /path/x" > .dsh/snapshots/<task>/<hash>.r1
```

文件名用路径 hash，另存一张映射表（远程路径 → 快照文件）。

回滚就是反向：`scp` 或 `ssh "cat > /path/x"` 把快照内容写回去。

**注意**：这条要求 SSH 执行器能"插入前置动作"。你的 SSH 工具现在是裸执行，需要包一层——所有 `write/edit` 类远程操作，先在本地留档再执行。这也是 `PreToolUse hook` 的另一个用途：不用改 SSH 工具本身，用 hook 读取参数、提前备份。

## 四、和审批闸门的关系

两者是一对：

```
危险命令 → 拦截（事前）→ 你确认 → 执行 → 存快照 → 可回滚（事后）
```

**只做拦截不做回滚**：你还是不敢让它执行。
**只做回滚不做拦截**：你会频繁回滚。

两个一起上，才形成"可以放手但可控"的闭环。

## 五、优先级建议

| 步骤 | 工作量 | 价值 |
|---|---|---|
| 变更登记表 | 0.5 天 | 能回答"动了什么" |
| 本地文件快照 | 1 天 | 能回滚本地改动 |
| diff 渲染 | 1 天 | 能看见改了什么 |
| 远程文件快照 | 1 天 | 能回滚生产改动 ← **最重要** |
| 整批回滚（按 task） | 0.5 天 | 一键撤销一个任务的全部改动 |

先做**变更登记 + 远程快照**这两个，投入 1.5 天，解决最痛的部分。
