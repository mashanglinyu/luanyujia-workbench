## 1. 记忆生命周期 · P0

**机制一句话**：给注入加一道"写入门"——`scope` 必须落在在用场景名单里（大小写归一 + 别名表），写入时校验，注入时只认名单内的 scope。

**为什么现在做（有数据，不是感觉）**

1. **12 条记忆永远注不进 Blender 场景**：场景名是 `Blender`（`外壳\scenarios\*.json`），库里 scope 是 `blender`（12 行），`index.js:102` 用 `r.scope === scope` **严格等值**，大小写不一致 ⇒ 这 12 行永久不可达。
2. **4/10 场景没有对应 scope**：`Blender`、`DSH·GUI改造`、`<客户> OA 系统运维`、`自我复盘`（后者按设计不建，前三个是漏）。这些场景的候选池只剩 `全局` 4 行。
3. **实测命中率被 scope 过滤砍掉 2/3**：同一份 126 条真实提示词（`d4c016f0`，scope=`DSH·GUI改造`）跑插件自己的 `termsOf`/`search`：
   - 不过滤：**88.1%** 有命中，平均 2.41 条
   - `scope=DSH·GUI改造`：**27.0%** 有命中，平均 1.68 条
   - 日志里连续 5 条 `skip:nomatch · terms=12` 就是这么来的（12 个词全被 df 砍掉：候选池 4 行时阈值 `max(2, floor(4*0.1))=2`，`index.js:108`）。
4. **写入门不存在**：`memory_write` 有实现（`packages\fs\tool-fs-search\src\memory.ts:120-150`），去重只按 `sha256(scope|text)` 精确匹配，**没有来源校验、没有场景校验**；而实际 71 条全靠 `记忆库.mjs --import` 灌。

**接入点**

- `引擎\插件\记忆注入\lib\index.js:102`（scope 严格等值）· `:108`（df 阈值）· `:151`（`MAX_PER_SESSION=12`）· `:169-172`（会话内 WeakMap 去重）· `:135`（90 字硬截断）
- `引擎\packages\fs\tool-fs-search\src\memory.ts:57`（writeMemory 的 idem 口径）
- `工具\记忆库.mjs:74`（`add()`）· `:183`（`--add`）
- `工具\记忆体检.mjs:99-101`（只统计 §〇，不碰 db）

**最小实现（≤1 天，约 60 行）**

1. `记忆注入` 里加 `normalizeScope()`：读 `外壳\scenarios\*.json` 的 `name` 列生成 `lower→正名` 映射，`blender → Blender`；比对时两边都 `toLowerCase()`。
2. `记忆库.mjs` 增加 `--scopes` 清单校验：`--add` 时 scope 不在名单内直接报错并列出最近邻（避免 `视频全工作流` vs `视频工作流` 这种 1 条孤岛）。
3. `记忆体检.mjs` 增加一项硬判据：**每个在用场景的可达行数 ≥ 5**，不足报 ⚠ 并打印缺哪个 scope。
4. df 阈值改成 `max(2, min(7, floor(pool*0.3)))`——池子只有 4 行时仍然过严，`0.1` 系数是给 70 行库设计的。


## 2. 任务板 canary → primary · P2

**机制一句话**：primary 的判据不是"切开关"，而是"板上出现**原生**生命周期事件"——现在 48/48 都是 `imported:*`，等于一面镜子，切过去也照不出新东西。

**为什么现在做**

- `--sync` 输出"新增 0，跳过 2，过滤 344"：过滤 344 = 旧台账 344 条（**没灌进来**），跳过 2 = 两条新派单**已在板内**。canary 想证明的两件事（不漏灌旧任务、不丢新派单）**各自只证明了 2 个样本**。
- 板里 `status` 只有 `delivered(34)` + `accepted(14)`，`evidence` 全是 `imported:rpc` / `imported:ack`；`task_event` 只有 `import(100)` + `submit(48)`，**`claim` 事件 0 条、`lease_until` 非空 0 条**。可 `--claim/--heartbeat/--deliver/--accept` 全都实现了（`任务板.mjs:338-343`）。
- 结论：**没有任何一个 agent 或场景真的在用这块板**，canary 期的问题是"样本量"和"使用者"，不是"水位"。

**接入点**：`工具\任务板.mjs:164-171`（canary/since 双过滤）· `:286-292`（`--canary` 列表水位）· `:129-134`（`ledgerStatus`，见第 8 条）· `工具\通知场景.mjs:1090-1095`（**唯一自动写入点**）。

**最小实现（≤1 天）**

1. **制造真实流量而不冒险**：加 `--replay <小时数> --db <副本>`——把最近 N 小时台账回放进一份 db 副本，输出"若切 primary 会多进哪些、哪些会被判错"，不碰主库。1 小时可做。
2. **切 primary 判据写进脚本**：`--promote-check` 返回 0/1，判据三条：`canary 期 ≥7 天 且 新派单 ≥20`、`台账↔板 按 hash 对账 漏灌 0`、`原生事件 ≥1/天`。当前：2/20 → **不许切**。
3. **回退开关**：把 `通知场景.mjs:1094` 那行 `--sync` 用 `DSH_BOARD_SYNC=off` 包一层；关掉即"板降级为只读镜像"，不删数据、不动水位。

**可测判据**：`node 任务板.mjs --promote-check; echo $?` → 现在应为 `1`（不通过）并打印三条各自的实际值；切完后 `task_event` 里 `claim` ≥1/天。

**风险 / 回退**：回放写副本无风险；`--promote-check` 只读。真正切 primary 前必须先做第 8 条（否则 `accepted` 是假的，判据会被污染）。

## 3. 启动安全：多代 LKG 有存无"可用" · P1

**机制一句话**：把"留 5 代"改成"留有效代 + 能一键 safe mode"，否则坏插件导致的启动失败可以无限循环。

**为什么现在做（三个硬事实）**

1. **5 代只覆盖 1 小时**：`generations` 现存 `gen-20261021205618 / 205619 / 212753 / 212754 / 220012`——最短间隔 **1 秒**，全部落在 20:56–22:00。`引擎快照.mjs:98-99` 是"按份数砍"，反复重启一次就把跨天的好点冲掉了。
2. **快照不含插件代码**：`engine-good\meta.json` 备份 **18 个文件**，插件只备份 `package.json` / `README.md` / `cordis.patch.yml`；`插件\记忆注入\lib\index.js`（真正会跑坏的那份）**不在内**。`profiles\node_modules\dsh-plugin-*` 的 junction 清单也不在内。
3. **自动回退不重试、也不降级**：`main.js:436-449`，连续失败 `n>=2` 就 `--restore --yes`（回到 current 快照），然后 `resetBootFail()`。若坏因是"新加的插件"而非"配置"，restore 什么也没修，计数清零后**再来两轮**——没有安全模式，也没有放弃条件（`engine-boot-fail.json` 现在 `count:0`）。
4. 旁证：`engine-good\pre-restore-*` 已堆 **3 份**（09:18、21:16、21:16），`restore()` 只写不清（`引擎快照.mjs:121-128`）。

**接入点**：`工具\引擎快照.mjs:87-99`（save 分代 + 保留 5）· `:117-146`（restore，无 prune）· `外壳\main.js:435-449`（`n>=2` 自动回退）· `:370-383`（`markEngineGood` 每次启动成功都 `--save`）。

**最小实现（≤1 天）**

1. **去重 + 按天保留**：`--save` 前比对 `meta.head + cordis.patch.yml 的 sha`，三者都没变就跳过；保留策略改成"最近 7 天每天 1 份 + 最近 3 份"。
2. **扩快照范围**：`meta.files` 增加 `插件\*\lib\*.js`（当前 9 个插件，体积约 1.1 MB → 3 MB 量级）与 `profiles\node_modules` 的 junction 名单（只存"名字→目标"的 JSON，不复制内容）。
3. **safe mode（最小版）**：`main.js` 在 `n>=3` 时先写一个 `插件\*.disabled` 标记（把 `profiles\node_modules\dsh-plugin-*` 重命名成 `.disabled`），再 `--restore`，然后**自动重试一次**；起得来就把禁用名单写进启动日志并在顶栏标"安全模式"，让用户点一下"逐个恢复"。
4. `pre-restore-*` 超过 5 份时删最旧（`restore()` 里加 3 行）。

**可测判据**

```bash
node <DSH根>\工具\引擎快照.mjs --list            # 期望：代数 ≥3 且时间跨度 ≥7 天（现在 5 代跨 1 小时）
node -e "console.log(Object.keys(require('<DSH根>\<路径>').files).length)"  # ≥27（18 + 9 个 lib 入口）
```
故障演练：故意在 `插件\记忆注入\lib\index.js` 顶部抛异常 → 连续重启 3 次 → **第 3 次能起来且日志出现"安全模式"**（现在会无限循环）。

**风险 / 回退**：safe mode 会临时禁用插件，可能让界面缺卡 → 只禁用"最近 24h 内改动过"的插件（按 mtime 过滤），其余不动；`pre-restore` 目录保留，手工可回到任意一刻。

## 4. 审批：`confirm` 是模型自填的软闸 · P1

**机制一句话**：把 `apply_patch` 的 `confirm:true` 换成真正的 `ctx.approval.request()`，让"多文件/敏感路径"由人而不是模型签字。

**为什么现在做**

- 判断条件是一行正则 + 模型自己填的布尔值：`packages\fs\tool-fs\src\apply-patch.ts:153-159`——`risky` 只看 `patches.length > 3` 或路径命中 `(AGENTS\.md|\.dsh|profiles|工具|启动器|\.env|package\.json|\.credentials)`；`args.confirm !== true` 才抛错。模型只要写 `confirm:true` 就过。历史上 `approval/asked` 事件全库 **1 条**（且不是 apply_patch 产生）。
- 正则已修（上一轮的 `$` 锚定问题没了），但**它只是"拦一下模型"，不是"问一下人"**。
- 引擎里现成有正确范式：`fs\tool-fs\src\sandbox.ts:96-104` 就是 `approver: this.ctx.get('approval')` + `approveEscalation(...)`；`ApprovalService.request()`（`interaction\user-approval\src\index.ts:206`）在**无 answerer 时返回 `'unavailable'`（fail closed）**。

**最小实现（≤0.5 天）**

1. `apply-patch.ts` 的 `risky` 分支改成：`const ap = ctx.get('approval'); const out = ap ? await ap.request({ agent, toolName: 'apply_patch', callId, reason }) : undefined; if (out !== 'allowed-once') throw new Error('[approval] apply_patch …')`。
2. **headless 兼容**：加 `DSH_APPROVAL_APPLY_PATCH=off|ask`（默认 `ask`）。`off` 时退回今天的 `confirm` 行为。理由：无 answerer 时 `request()` 必然 `unavailable`，脚本化批量改文件会全挂，必须有逃生阀。
3. `confirm` 参数保留但语义改为"仅 `off` 模式下有效"，并在描述里写明。

**可测判据**：造一个 4 文件 patch → 会话里必须出现 `approval/asked` + `approval/decided` 成对事件；`DSH_APPROVAL_APPLY_PATCH=off` 时同样 patch 无 `approval/*` 事件且照旧执行（回归不变）。

**风险 / 回退**：交互式场景会多一次点击（这是目的）；UI 若没渲染 answerer，用户会看到"失败"而不是弹窗——所以**先确认 answerer 存在**（`main.js` 侧要处理 `approval/asked`），否则等于把功能关死。回退：环境变量置 `off`。

## 5. 体检：⚠ 没有"年龄"，所以永远没人认领 · P1

**机制一句话**：给每条非 ✅ 项发一个稳定 hash，记 `firstSeen / owner / due / ack`，让"这条 ⚠ 挂了几天"变成可查询的数字，而不是每次被覆盖写冲掉。

**为什么现在做**

- 报告是**覆盖写**：`全量标准化体检.mjs:2340`（`reportPath`）、`:2349`（月报同月覆盖成"本月最后一次"）。今天的 `体检报告.md`：70 项 ✅61 ⚠9 ⛔0——**下一轮跑完，这 9 条去哪了没人知道**（修好了还是没修，看不出来）。
- `owner` 只以文本形式嵌在 `fix` 末尾（`…（dg-dsh）`，见 `:891`、`:1055`、`:1522`），**不是字段**，无法统计"谁欠了几条"。
- 已有反面教材：`记忆体检` 报 `⛔0 ⚠0`，而实际有 3 个场景注入可达行数为 0（见第 1 条）——**体检的"绿"不等于机制的"通"**。

**接入点**：`工具\全量标准化体检.mjs:2340-2341`（写报告 + 写 `_体检-latest.json`）· `:2321`（"要看历史看月报"）· `工具\记忆体检.mjs:99-101`（统计口径）。

**最小实现（≤1 天）**

1. 每条非 ✅ 项算 `hash = sha1(section + '|' + text)`，append 到 `外壳\data\体检条目台账.jsonl`：`{hash, firstSeen, lastSeen, owner, due, ackAt, status}`。
2. `owner` 从 `fix` 里用正则 `（([a-z\-]+)）$` 提取（现有 9 条里 7 条带），提不到就记 `未指派`。
3. 报告尾部加一段硬数字：`存活 >72h 且未认领：N 条（最老 Xh：<text>）`；N>0 时把总评从"✅ 无急修"改成 ⚠。
4. 新增 `体检认领.mjs --ack <hash> --by <面板>`（10 行），只写 `ackAt`。

**可测判据**：连跑两次 `node 全量标准化体检.mjs`，同一条 ⚠ 的 `firstSeen` **不变**、`lastSeen` 前进；报告尾部出现"存活 >72h N 条"。一周后 N 应为 0（否则就是真的没人管）。

**风险 / 回退**：条目文本里带数字（"1 个新目录"）会让 hash 抖动 → hash 前先去掉数字再算。台账是追加文件，删掉即回到今天的行为。

## 6. 可观测 / 成本：有数据，缺"什么时候该停" · P2

**机制一句话**：不给顶栏加卡，只给账本加一个阈值出口（`--guard`），把"这一回合贵到该压缩了"变成退出码。

**为什么现在做（真数）**

- `node 回合账本.mjs --since "2026-10-21 20:00"`：**9 会话 / 363 回合 / promptMiss 17,970,084 / cacheRead 2,289,864,556 / output 4,007,279 / 工具调用 6576**。缓存命中 99.2%，所以"工具集变化打缓存"不是主要成本（`d4c016f0` 45 次 header 变 14 次，missingRate 仅 1.0%）。
- 贵是**单回合**贵：最贵回合 `promptMiss 1,291,997 / cacheRead 8,328,576`；`bc69b89c` 最贵 `promptMiss 660,004 / cacheRead 20,692,096`。这类回合之后继续硬跑，等于每步重付一次 8M 的读缓存。
- 顶栏**完全没有**成本入口：`renderer\topbar-status.js` 里 `成本|账本|token|cacheRead|promptMiss` 命中 **0**；`main.js` 里"回合账本"命中 **0**——账本是纯手工 CLI。

**接入点**：`工具\回合账本.mjs:102`（`--since`）· `:110-120`（汇总与"最贵回合"）· 钩子可用 `core/agent-loop/src/agent.ts:387`（`turn/end`）。

**最小实现（≤0.5 天）**

1. `回合账本.mjs --guard [--sessions 1]`：读最新会话，任一回合 `promptMiss > 600K` 或 `cacheRead > 8M` → 打印一行建议（"该压缩/换会话"）并 `exit 1`。
2. 挂到 `turn/end` 的轻量插件（或 `外壳` 定时 5 分钟跑一次），命中就 append 一行到 `外壳\data\成本告警.log`。

## 7. 工具披露：已经量过，答案是"不需要 RAG" · 明确不做

**机制一句话**：维持静态 `excludeTools` 裁剪，不做每回合动态工具检索。

**证据（18 会话 / 1168 回合 / 13,167 次调用）**

## 8. 协作回执：`ack` 冒充 `accepted`，完成态从未存在 · P0

**机制一句话**：把"收到知悉"和"验收完成"拆成两个状态，否则板上的"完成率"是假的，回执闭环率 100% 也是假的。

**为什么现在做（这是本轮最硬的一处）**

- 建板时就把 `ack` 映射成 `accepted`：`任务板.mjs:129-134`
  ```js
  if (e.ack && (e.ack.time || e.ack.by || e.ack.note)) return { status: 'accepted', evidence: 'imported:ack' }
  ```
- 于是 48 条里 **14 条 `accepted`，evidence 全是 `imported:ack`**，`34` 条 `delivered`（`imported:rpc`）——**真正走 `--accept` 的 0 条**（`task_event` 只有 `import/100` + `submit/48`）。
- `回执哨兵.mjs:228-241 autoCloseSettled()` 又把对方的 `【不需要回执·知悉】` 直接写成 `ack`（"收到对方知悉自动销账"），所以 体检 那项"24h 内需回执的都已闭环（需回执 123 条 · 未 ack 0）"是**这条自动销账造出来的**，不是真闭环。
- 真断点就是这个：**长任务只证明"消息到了"，没有"活干完了"的信号**。板有 `--deliver/--accept` 却没人用；`lease_until` 非空 0 条，所以卡住也没人知道。

**接入点**：`工具\任务板.mjs:129-134`（ledgerStatus）· `:338-343`（claim/heartbeat/deliver/accept）· `工具\回执哨兵.mjs:224-241`（autoClose）· `工具\待回执.mjs:209`（"不需要回执"例外）。

**最小实现（≤2 小时）**

1. `ledgerStatus` 拆三档：只有 `ack` ⇒ **`acknowledged`**（新状态，加入 `STATUS` 数组 `:49`）；`delivered` 保持；`accepted` **只由 `--accept`/`finish()` 产生**。
2. 哨兵 `autoCloseSettled` 继续写 `ack`（保留销账语义），但**不再影响 status**。
3. `--stats` 增列：`acknowledged N / accepted M`，并打印"需回执但从没 deliver 的：K 条"。（按当前数据：26 条 `expects_receipt=1` 里 14 条 acknowledged、12 条只有 delivered ⇒ K≈12 会第一次浮出来。）

**可测判据**：`node 任务板.mjs --stats` 从 `delivered 34 / accepted 14` 变成 `delivered 34 / acknowledged 14 / accepted 0`；`SELECT COUNT(*) FROM task WHERE status='accepted' AND evidence LIKE 'imported:%'` = **0**。体检"通知闭环"会从 ✅ 掉到 ⚠——**这是变诚实，不是退化**。

**风险 / 回退**：状态枚举变化会影响一切读 `accepted` 的地方（体检、回执哨兵、看板 UI）→ 先在 `--stats` 里并存打印一版，确认无脚本依赖 `accepted` 再落库；回退只需把 `STATUS` 里的 `acknowledged` 去掉。
