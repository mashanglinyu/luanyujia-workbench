# 任务与自动化

## 一、任务工具（6 个，别多）

```
TaskCreate   创建，返回 id
TaskGet      取单个详情
TaskUpdate   改状态（pending → in_progress → completed）
TaskList     列全部
TaskStop     停掉运行中的（返回的 agent_id 就是 task_id）
TaskOutput   取输出（block:true 等完成 / false 看进度）
```

提示词里对"什么时候用"限制得很死（`task-management.md` 全文）：

```markdown
<task_management>
Use the task management tools (TaskCreate, TaskGet, TaskUpdate, TaskList) only when:
- The user's request has multiple distinct, independently verifiable execution steps (typically 3 or more).
- The user explicitly asks you to plan, break things down, or list todos.

Do not use them for anything a single response or a single tool call can resolve, 
or for requests with only one straightforward step. Answer or execute directly.

Once you have created tasks, keep their status accurate:
- Call TaskUpdate to mark a task as in_progress before you start working on it.
- Call TaskUpdate to mark it as completed immediately after it is done — do not batch up multiple completions.
- Never mark a task as completed if the work is only partially done or you hit an unresolved error; leave it in_progress instead.
</task_management>
```

两句话值得单独拎出来：

> **do not batch up multiple completions**（不许攒批标记完成）

原因：任务状态是用户看进度的唯一信号。攒批会导致"看起来一直卡着，突然全绿"。DSH 的面板如果要显示进度，这条是前提。

> **Never mark a task as completed if the work is only partially done or you hit an unresolved error; leave it in_progress instead.**

"做了一半别标完成"——这条防的是模型为了"看起来干完了"而虚报。这在运维场景里是致命的（你看到全绿就不管了）。

## 二、任务的粒度和状态机

【实证】从运行时的日志与类名反推，WorkBuddy 的任务状态不止四种：

```
pending → running → completed
              ↓
           failed
              ↓
        cleanup（释放子会话/子进程）
```

`AgentTask.cleanup()` 里有段逻辑很细：团队成员的子会话是否要保留 history-only 记录：

```js
// 非团队成员 或 已请求释放 → 释放 subAgentSession 引用
// 团队成员 → 保留 history-only 的 team session（sessionId / storeId / historyLen 都留着）
```

**为什么**：团队协作里，一个成员的会话结束了，但它的历史还要被其他成员查询。全释放就断了上下文。

## 三、自动化（定时任务）

【实证】`automation_update` 工具的字段设计：

```ts
{
  mode: 'list' | 'view' | 'create' | 'update' | 'delete',
  name, prompt,
  scheduleType: 'once' | 'recurring',
  scheduledAt: '2026-10-20T14:30',        // once 用
  rrule: 'FREQ=WEEKLY;BYDAY=SU;BYHOUR=9;BYMINUTE=0',  // recurring 用
  validFrom, validUntil,                  // 有效期窗口
  status: 'ACTIVE' | 'PAUSED',
  cwds,                                   // 工作目录
}
```

RRULE 是标准 **RFC 5545**，不是自己造的 cron 语法。好处：一个表达式能表达"每周一三五 9 点"（`BYDAY=MO,WE,FR`）、"每月 1/15/28 号"（`BYMONTHDAY=1,15,28`），不用建多条。

几个约束值得抄：

- **`FREQ=HOURLY` 时不要加 `BYHOUR/BYMINUTE`**（会冲突）
- **一次性 vs 周期**用 `scheduleType` 分开，不给 rrule 塞 `COUNT=1` 这种取巧
- **`validFrom/validUntil` 单独于 rrule**，"3 月 18 到 22 号之间每天跑"用两段表达，不污染重复规则

### 提示词里最实用的一条

> Make the prompt self-contained. Future runs will not see the current conversation, so any company name, file path, metric definition, URL, or user preference mentioned now must be written into the prompt explicitly.

**"未来运行时看不到当前对话"** —— 这是所有定时任务设计的第一原则，也是最容易忘的。

DSH 的"每周日体检"如果做成定时任务，prompt 里必须写全：
- 哪台机器、什么端口
- 8 个检查项分别是什么、判定标准
- 报告写到哪个目录、命名规则
- 发现问题时通知谁

不能写"按上次说的那样跑一遍"。

## 四、DSH 的改造动作

### 4.1 任务化（中等工作量，但结构收益大）

现在的组织是"面板 = 会话"。改成：

```
任务 (task)
├── id / 标题 / 创建时间
├── 状态机
├── 关联会话（一个任务可能跨多个会话）
├── 产物集（这个任务产出的所有文件）
└── 快照集（这个任务改过的文件版本）
```

左栏列表按"项目 → 任务"两级分组。这是 WorkBuddy 侧边栏的结构，也是你截图里 `任务清单` 文件夹想表达但还没做的。

最小可用版：**任务 = 带名字和时间范围的会话**，产出文件自动归到该任务下。不需要一开始就做完整状态机。

### 4.2 定时体检（小工作量，直接见效）

你已经有 8 类检查项的定义了，做成：

```json
{
  "name": "OA 系统周检",
  "scheduleType": "recurring",
  "rrule": "FREQ=WEEKLY;BYDAY=SU;BYHOUR=3;BYMINUTE=0",
  "prompt": "对 47.108.x.x 上的幼儿教育 OA 系统执行 8 类检查：\n1. CPU/内存/磁盘水位（阈值：磁盘>85% 告警）\n2. nginx 状态与 5xx 比例（阈值：>1% 告警）\n3. mysql 连接数与慢查询（阈值：慢查询>10/分钟）\n4. backend/lanchain-oa 服务存活\n5. 端口 8081/8082/8083 可达性\n6. SSL 证书剩余天数（<30 天告警）\n7. 磁盘日志文件增长（>1GB 单项告警）\n8. 备份文件完整性（最新备份距今 <48h）\n\n全部只读，不执行任何写操作。\n报告写入 <盘根>\\工作台\\体检报告\\YYYY-MM-DD.md，并与上周报告对比差异。\n有任一项 FAIL 时在报告开头用【需要处理】标注。",
  "status": "ACTIVE"
}
```

注意 prompt 里写了"全部只读"——配合只读模式跑，双保险。

### 4.3 别做的

- 别自己发明 cron 语法，用 RFC 5545 RRULE（现成库很多）
- 别把定时任务做成"后台静默跑"。结果必须有地方落（报告文件 + 会话列表置顶），否则等于没跑
