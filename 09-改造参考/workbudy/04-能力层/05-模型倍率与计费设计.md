# 模型倍率与计费设计（实证）

> 数据来源：`cli/product.json` 的 `models` 数组，58 条，每条带 `credits` 字段。
> 这不是猜测，是它自己的定价表。

---

## 一、定价不是按 token 算的，是按「倍率」

```json
{ "id": "default", "credits": "x2.00 credits", ... }   // Claude-3.7/4 Sonnet 系列
{ "id": "deepseek-v4.1-flash", "credits": "x0.03 credits", "maxInputTokens": 1000000 }
{ "id": "hy3", "credits": "x0.00 credits", "maxInputTokens": 192000 }
```

**`default` 是基准，x2.00。其他模型全部相对它打折。**

完整定价表（有 `credits` 的 13 个）：

| 倍率 | 模型 | 上下文 |
|---|---|---|
| x0.00 | **hy3**（混元3） | 192K |
| x0.03 | **Deepseek-V4.1-Flash** | 1M |
| x0.05 | hy3-x | 192K |
| x0.06 | GLM-5.3-Flash | 1M |
| x0.14 | GLM-5.3-FlashX | 1M |
| x0.17 | Deepseek-V4-Flash | 1M |
| x0.25 | MiniMax-M3 | 512K |
| x0.29 | Hy4 preview / preview-x | 1M |
| x0.51 | Deepseek-V4-Pro | 1M |
| x0.57 | Kimi-K2.7-Code | 256K |
| x0.77 | Kimi-K2.8-Preview | 1M |
| x0.79 | GLM-5.3 / 5.2 | 1M |
| x1.62 | Kimi-K3 | 1M |
| x2.00 | Default（Claude） | 200K |

**从 x0.03 到 x2.00，跨度 66 倍。** 而 x0.03 的那个上下文是 x2.00 的五倍。

另外 44 个模型**没有 `credits` 字段**——包括 kimi-k2.6、minimax-m2.5/m2.7、glm-5.0、deepseek-v3.2、hunyuan-chat、`auto`，以及全部图片/视频模型（hunyuan-image、kling-video）。没有定价通常意味着：不在积分体系内、走单独计费、或已下线只留 ID。

---

## 二、为什么敢有免费模型：三层原因

### 1. 成本结构真的变了

一个 1M 上下文、支持工具调用的模型标 x0.03，等于"跑一次对话的成本是 Claude 的 1.5%"。
国产开源权重模型 + 自建推理，边际成本接近电费。**免费不是让利，是成本真的低到可以让。**

### 2. 免费的是「模型」，不是「能力」

这点最关键。积分消耗不只看 token：

- 文件解析
- 浏览器操作
- 图片/视频生成
- 长上下文的反复读

用 0 倍率模型，这些开销照扣。所以"免费模型"把你拉进产品，但不等于让你白嫖整个 Agent。**门槛设在入口，不在过程。**

### 3. 它是定价阶梯的第一级

```
x0.00  引流     够用但不够好，零成本跑通闭环
x0.03  主力档    成本几乎可忽略，撑住日活
x0.5-0.8 进阶档  明显更好，价格可感知
x1.6-2.0 顶配    留给真正需要的人
```

用户在免费档跑通了「建任务 → 对话 → 出产物 → 拿积分」的完整闭环，才有动机往上走。**没有免费的入口，付费转化率会低得多。**

---

## 三、倍率制比按 token 计价好在哪

对 DSH 这类自建工作台，这个设计可以直接抄：

| 维度 | 按 token 计价 | 倍率制 |
|---|---|---|
| 用户理解 | 要算 token，看不懂 | 「这次花了 0.03 倍」，直观 |
| 调价 | 改配置 + 改展示 + 改账单逻辑 | **只改一个数字** |
| 做活动 | 要加一套优惠券逻辑 | 某个模型临时设 x0.00 |
| 跨模型比较 | 单位不同，没法比 | 同一把尺子，直接比 |
| 成本核算 | 反推 token → 成本 | 倍率 × 基准价，一步到位 |

**核心优势：把"成本"和"价格"解耦。** 成本涨了不改价，价改了不改成本模型。

## 四、顺带一个实证：压缩阈值按模型调

```json
"tokenUsageThresholds": {
  "inputTokens": { "warning": 0.6, "critical": 0.7, "emergency": 0.9, "preMessage": 0.5 },
  "compact": { "emergency": 0.4, "modelOverrides": { "deepseek": 0.5 } },
  "request": { "emergency": 0.9 },
  "summary": { "emergency": 0.15 }
}
```

两个观察：

1. **`preMessage: 0.5`** 印证了上一份文档的结论——到半窗就在发消息前预备压缩。
2. **`compact.modelOverrides.deepseek = 0.5`** —— DeepSeek 单独设了 0.5 的压缩线，比其他模型的 0.4 更早。说明它按模型的实际表现调参，不是一刀切。

**这是"倍率制"思维的延伸**：不只价格可以按模型分级，行为参数（压缩阈值、重试次数、超时）也应该按模型分级。

---

## 五、对 DSH 的两条建议

1. **如果你的工作台要展示成本，用倍率不用 token。** 用户不想看 `输入 12483 / 输出 2210 / 缓存命中 63%`，他想看「这次 0.03 倍」。你现在面板上的 token 统计留着给运维看，给用户看的应该是钱。

2. **给每个模型单独配行为参数。** 尤其压缩阈值——小窗口模型（96K）和大窗口模型（1M）用同一条压缩线，必然一个太早一个太晚。
