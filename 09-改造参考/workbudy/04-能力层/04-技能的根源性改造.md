# 技能的根源性改造：从「目录 + 索引」到「触发面 + 渐进披露」

> 这份不是功能清单，是**范式修正**。DSH 现在的技能系统是"目录 + 索引"，手感生硬。
> 生硬不是写得不够好，是组织方式选错了。这份讲为什么错、错在哪一层、怎么换。

---

## 一、根因：三种错配

### 1.1 空间组织存放时间知识

目录树回答的是**「东西在哪」**。技能要回答的是**「什么时候该用我」**。

AI 没有浏览行为。它不会沿着目录一层层走进去看，只会拿当前情境去匹配一句描述。
所以：**索引越长，匹配越难。你越努力整理，它越不好用。**

这是反直觉的——人类查资料靠"目录 → 章节 → 页"，所以直觉上会照搬。但模型的检索是**语义相似度**，不是**路径导航**。

### 1.2 名词结构装不下动词知识

```
目录能装： "库表结构说明"  "部署环境清单"  "家长端话术模板"
目录装不下： "改字段要先备份 → 再迁移 → 再通知家长端，失败就回滚"
```

第二句有**顺序、判定分支、退出条件**。目录树是层级结构，表达不了这些。
把流程硬塞进目录，只能塞成"流程说明.md"，然后模型读完还要自己解释一遍——每次都解释，每次都可能偏。

### 1.3 单层承载了本该三层的东西

现在索引 = 全部内容。而实际上有四类东西被混在了一起：

| 类别 | 特征 | 该在哪一层 |
|---|---|---|
| 路由信息 | 极短、决定"要不要用" | 常驻元数据 |
| 流程知识 | 中等长度、有顺序 | 触发后读 |
| 事实资料 | 长、需要精确 | 按需查（references） |
| 确定性动作 | 有唯一正确结果 | 直接跑（scripts） |

四类混一层 → 索引又长又没用，正文又读不完，脚本还得模型手敲。

## 二、四条转换

### 转换一：索引不是资产，是视图

**现状**：手工维护一份索引文件，新增技能要回去改索引 → 索引必然滞后 → 滞后就生硬。

**改成**：没有索引文件。每个技能在自己的 `SKILL.md` frontmatter 里声明元数据，系统启动时扫目录、收集、拼装成列表。

```yaml
---
name: oa-deploy
description: 当需要发布幼儿教育 OA 到生产、回滚上一版本、或排查发布后 502 时使用。覆盖 nginx reload、备份、回滚三步。
allowed-tools: [Read, Bash, Grep]
---
```

**关键**：人只写"我什么时候该被用"，汇总交给系统。加一个技能 = 建一个目录，不需要动任何索引。

这和数据库的「视图 vs 物化视图」是同一个道理——索引是物化视图，会腐化；元数据是基表，永远最新。

### 转换二：常驻的只能是触发句

官方规范的硬规矩（`skill-creator/SKILL.md` 原文）：

> **Use the third-person** (e.g. "This skill should be used when..." instead of "Use this skill when...").
> Be specific about what the skill does and when to use it.

为什么是第三人称？因为 description 会被**拼进系统提示**，视角是"关于这个技能的事实陈述"，不是"对模型的命令"。写成"用这个技能当…"会让模型误以为用户在命令它。

**写法对照**：

| ✗ 摘要式（不能路由） | ✓ 触发式（能路由） |
|---|---|
| OA 系统说明 | 当需要查 OA 库表、写跨表 SQL、确认字段含义时使用 |
| 数据库文档 | 当 SQL 报错、要确认索引、或改表结构前评估影响时使用 |
| 部署流程 | 当需要发布到生产、回滚版本、或发布后出现 502 时使用 |

**判据**：description 里必须有**用户会说的话**。"502"、"回滚"、"跨表"，这些是触发词；"说明"、"文档"、"流程"不是。

### 转换三：最好的技能，是模型不读的技能

三层里最容易被忽略的是第三层：

> Bundled resources — As needed (Unlimited*)
> \* Unlimited because **scripts can be executed without reading into context window**.

原文这句是精髓。**确定性步骤写成脚本，模型只调用、只读输出，实现永远不进上下文。**

对照一下：

- 现在：模型读"部署流程.md" → 理解 → 自己拼 `nginx -t && systemctl reload nginx` → 可能漏掉备份
- 改后：模型执行 `python scripts/deploy.py --env prod` → 读 stdout → 报结果

差别不只是省 token，是**结果确定性**。脚本每次都一样，模型每次都可能不一样。

**判据**：一段步骤，如果让两个工程师执行会得到相同结果 → 写成脚本。如果需要临场判断 → 留在正文。

### 转换四：技能自带边界，不只是知识

frontmatter 里的 `allowed-tools` 声明"这个技能能碰哪些工具"。

```yaml
allowed-tools: [Read, Grep]        # 只读技能，不可能写出事故
allowed-tools: [Read, Bash]        # 可执行
```

技能不只是"知道什么"，还是"被允许做什么"。配合三档权限模式，技能成为**权限的第二层细化**——全局放开 Bash，但 `db-schema` 这个技能只能 Read/Grep。

## 三、判决表：一条知识该放哪

这是整套改造里最实用的一张表。遇到任何一条不知道该放哪的内容，查这里：

| 这条东西的性质 | 放哪 | 为什么 |
|---|---|---|
| 反复执行的固定步骤 | `scripts/` | 不进上下文，结果确定 |
| 需要查证的事实（表结构/接口/端口/账号位置） | `references/` | 按需读，不常驻 |
| 「什么时候该我上」的判定 | `SKILL.md` 的 `description` | 唯一常驻的东西 |
| 跨任务的长期偏好约定 | 记忆 `MEMORY.md` | 不属于某个技能专属 |
| 本次任务的一次性约束 | 当次提示词 | 不该沉淀 |

**判据链（按顺序问）**：

1. 这一步会重复执行吗？→ 会 → 写脚本
2. 这是一份需要精确查的事实吗？→ 是 → references
3. 这是"什么时候用"的判定吗？→ 是 → description
4. 这是跨任务的偏好/约定吗？→ 是 → 记忆
5. 以上都不是 → 一次性约束，留在当次对话里，别沉淀

绝大多数「生硬」，都是把第 1、2 类塞进了第 3 类。
**你现在的索引，本质上是一份 `references`，被误当成了路由表。**

## 四、三条更上层的（不在技能范围内）

技能只是"程序性知识"这一格。同一层还有三处用了同样错误的组织方式。

### 4.1 提示词要片段化，不要一整篇

WorkBuddy 的做法：`prompt-common/fragments/` + 每个模式自己的 `fragments/`，用 `{% include %}` 拼装。

好处：
- 同一条规则多个模式共用（改一处，全局生效）
- 模式切换 = 换片段集合，不是换一整篇 prompt
- 每段职责单一，可以单独 review、单独测试

**DSH 的现状**：系统提示应该是一大块，改一句话要担心影响全文，也没法给不同模式复用不同部分。

**改造**：拆成 `fragments/` 目录，一段一个职责，按模式组合。

参考：`06-原始资产/4-提示词片段/`、`03-Agent运行时/05-提示词工程与注入防护.md`

### 4.2 上下文是"持续重写"，不是"存全量"

你现在靠"当前交接"覆盖写，短任务会丢细节。根因不是覆盖写，是**只留一份摘要、没有分层**。

正确的模型：
- **全量落盘**（transcript 永远完整存在于磁盘，可回溯）
- **分层摘要**（当日日志 → 项目 MEMORY.md → 会话内 compact 摘要）
- **锚点保留**（用户原话、文件路径、未完成的决定，这三类永不被压缩掉）

摘要可以重写，锚点不能丢。区分这两者，就是压缩策略的全部。

参考：`03-Agent运行时/03-上下文压缩与记忆注入.md`

### 4.3 工具的 description 就是提示词

模型只能通过 description 认识工具。这一层的措辞直接决定行为质量。

对照：

| ✗ | ✓ |
|---|---|
| 执行 SQL | 对生产库执行只读查询，返回结果集不含敏感字段，超过 1000 行会截断 |
| 写文件 | 覆盖写入本地文件。**注意：会覆盖已有内容，不做备份** |
| SSH 连接 | 以 root 身份连接生产主机执行命令。**高危，需审批** |

写清楚**后果**和**边界**，模型才会谨慎。只写动作，模型就会当成普通函数调用。

## 五、动手顺序

不用重建技能系统。三步，一晚能做完第一步。

### 第 1 步：删掉索引，加 frontmatter（半天）

- 删掉手写索引文件
- 每个技能目录的 `SKILL.md` 加 3 行：`name` / `description`（写成触发句）/ `allowed-tools`
- 启动时扫 `.dsh/skills/*/SKILL.md`，读 frontmatter，拼列表

**验收标准**：新增一个技能目录，重启后自动出现在列表里，不需要改任何其他文件。

### 第 2 步：把最痛的三个流程写成脚本（一天）

优先选"步骤固定、错了会出事"的：

1. `deploy.py` —— 备份 → 发布 → health check → 失败自动回滚
2. `db-migrate.py` —— 迁移前 dry-run 输出影响行数
3. `health-check.py` —— 你那个 8 类体检，从"手动每周日跑"变成一条命令

**验收标准**：模型执行一条命令就完成，正文里不再出现具体命令序列。

### 第 3 步：拆提示词片段（两天）

- 按职责拆：身份 / 工具使用 / 结果呈现 / 记忆 / 安全边界 / 模式行为
- 每个模式（只读/计划/执行）组合不同片段
- 一次只迁移一段，迁移一段验证一段

**验收标准**：改一条安全规则，不需要通读整篇系统提示。

## 六、一句话总结

> **索引是给人看的，触发句是给模型看的。**
> 你现在这份索引，既没帮模型做判断，又增加了你维护的负担——两头不讨好。
