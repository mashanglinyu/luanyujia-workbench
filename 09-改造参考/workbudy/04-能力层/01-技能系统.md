# 技能系统

> 你的文案里已经讲了 SKILL.md 机制，而且讲得对。这份补的是**工程细节**——那些不讲就会踩坑的地方。

## 一、三级渐进加载（官方定义，直接引用）

`skills/skill-creator/SKILL.md` 原文：

> Skills use a three-level loading system to manage context efficiently:
> 1. **Metadata (name + description)** — Always in context (~100 words)
> 2. **SKILL.md body** — When skill triggers (<5k words)
> 3. **Bundled resources** — As needed by CodeBuddy (Unlimited*)
>
> \* Unlimited because scripts can be executed without reading into context window.

**"scripts 可以执行而不必读进上下文"这句是精髓**。你现在的做法是让 AI 读文档知道怎么做；更省的做法是**把确定性步骤写成脚本，AI 只负责调用和读输出**。

举例：`library` 技能底下有 `database/create_database.py`、`import_csv.py` 等十几个脚本，每个都配套一个 `entry.md` 说明。AI 调脚本，不读实现。

## 二、技能包的完整解剖

```
skill-name/
├── SKILL.md                 ★ 必需
│   ├── YAML frontmatter
│   │   ├── name:           必需
│   │   ├── description:    必需 ← 决定"什么时候用这个技能"
│   │   ├── allowed-tools:  可选，限定该技能能用的工具
│   │   └── disable:        false
│   └── Markdown 正文       必需（<5k words）
├── scripts/                 可执行代码（Python/Bash）
├── references/              按需加载的文档（schema、API 文档、政策）
├── assets/                  不加载进上下文，只用于产出（模板、图标、字体）
└── .codebuddy-plugin/       plugin.json（打包元信息）
```

frontmatter 实例（`skill-creator` 自己的）：

```yaml
---
name: skill-creator
description: Guide for creating effective skills. This skill should be used when users want to create a new skill (or update an existing skill) that extends CodeBuddy's capabilities with specialized knowledge, workflows, or tool integrations.
license: Complete terms in LICENSE.txt
allowed-tools:
disable: false
---
```

## 三、description 写法有一条硬规矩

原文：

> **Metadata Quality:** The `name` and `description` in YAML frontmatter determine when CodeBuddy will use the skill. Be specific about what the skill does and when to use it. **Use the third-person** (e.g. "This skill should be used when..." instead of "Use this skill when...").

为什么？因为 description 是被**拼进系统提示**的，视角是"关于这个技能的事实描述"，不是"对模型的命令"。写"用这个技能当…"会让模型以为用户在命令它。

还有一条：

> **Agent-Created Flag:** The YAML frontmatter MUST include `agent_created: true` so that `skill_manage` can modify or delete the skill later.

AI 自己造的技能要打标记，否则后续没法管理（分不清哪些是内置的、哪些是模型生成的）。

## 四、什么时候该写技能，什么时候不该

原文的判据（挑实用的）：

| 该写 | 不该写 |
|---|---|
| 同一段代码被反复重写 → 提炼成 `scripts/` | 一次性任务 |
| 每次都要重新发现的 schema/接口 → `references/` | 模型本来就知道的通用知识 |
| 每次都要重建的脚手架 → `assets/` | 一段很短的提示就能说清的偏好 |
| 公司私有规则/流程 | 易变的、需要每次现场确认的信息 |

再加一条原文提到的：

> **Avoid duplication**: Information should live in either SKILL.md or references files, not both. Keep only essential procedural instructions and workflow guidance in SKILL.md; move detailed reference material, schemas, and examples to references files.

**同一个信息只能存在于一个地方**。写在两处必然漂移。

## 五、写作风格：祈使句，不要第二人称

> **Writing Style:** Write the entire skill using **imperative/infinitive form** (verb-first instructions), not second person. Use objective, instructional language (e.g., "To accomplish X, do Y" rather than "You should do X" or "If you need to do X").

这条和 description 用第三人称是同一个道理：技能文档是**规格说明**，不是对话。

## 六、DSH 的改造动作

### 6.1 目录约定

```
.dsh/skills/
├── oa-deploy/SKILL.md          发布流程（你的私有知识）
│   ├── scripts/deploy.py
│   └── references/env.md       环境清单、端口、账号位置
├── db-schema/references/       ★ 表结构文档，AI 查库前必读
└── parent-report/              家长端话术模板
    └── assets/template.html
```

### 6.2 立刻能见效的三个技能

按你当前痛点排：

1. **`db-schema`** —— 把幼儿教育 OA 的库表结构写成 `references/`。现在 AI 每次查数据都要现场 `show tables` 摸索，这是纯浪费。这一个技能能省掉大量 token 和误判。
2. **`oa-deploy`** —— 发布流程（nginx reload / 备份 / 回滚步骤）写成技能 + 脚本。避免每次"AI 自由发挥"。
3. **`incident-playbook`** —— 服务挂了怎么办的分诊流程。你现在是每次重新推理，应该固化。

### 6.3 UI 侧

加一个只读面板，列出：
`技能名 | 描述 | 来源(user/project/builtin) | 是否启用 | 正文行数`

成本半天，但解决了"AI 现在会什么"这个黑盒问题——你文案里讲的"技能目录常驻是固定小开销"，用户看不见这个开销花在哪。
