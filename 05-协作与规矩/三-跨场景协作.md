## §二 用户 2026-10-16 定的十条新规矩（原话 + 落地写法）

### 规矩 1｜「清理的活全给本地电脑场景」——★ **不止工作区：任何场景的清理活都归它**（2026-10-16 用户明确）

- **全机清理专属助手 = `本地电脑`（`pc-cleanup`）场景**（面板 `pc-ai`）。**别的 9 条会话不要自己删/移东西**——标的**不限于**工作区 `<工作区>`：
  **工作区 / `备份\*` / 缓存与死重量 / 临时目录 / 盘容量与大户**，全都归它（四个辖区见技能 `pc-cleanup` §1）。
- **要清 → 给它的会话发消息**（首选，直达，不用等它开工）：
  `node <DSH根>\工具\清理请求.mjs "<要清理什么/在哪/为什么>" --from <你的场景>`
  —— 它走引擎 RPC `session/prompt` 把请求当**一个用户回合**发进 `pc-ai` 的会话；RPC 不通会自动降级，把同一句话落进 `引擎\场景项目信息\本地电脑\场景记忆` 的 `§〇`「工作区清理请求接收块」（并照样在 `外壳\data\pc-cleanup-requests.log` 留痕）。加 `--dry` 先看要发什么。
- 或者老办法：把「**路径 → 为什么 → 建议怎么处理**」写到它的交接处（`引擎\场景项目信息\本地电脑\场景记忆` 的 `§〇` 追加一行），或直接在 `pc-ai` 面板里说。格式见 §四。
- **你只管提请求，别动手**：提完就继续干你那份不涉及清理的活；它按"先只读盘点 → 出清单 → 要动手前先在面板回一句 → 动手 → 记三处"走。
- ⛔ **`清理请求.mjs` 只发消息**：脚本里不许出现 `Remove-Item`/`rmSync`/`del`，它自己绝不删/移任何东西。
- ⛔⛔ **删除分档（2026-10-17 用户拍板，取代 2026-10-16 的"一律只移不删"）**：**可再生类（缓存/临时/编译产物/过期安装包/日志/spill）可直接删**；**其它（用户文档/素材/媒体/会话库/备份/拿不准的）一律进回收站**。原则仍是"先列清单 + 等点头"（`Microsoft.VisualBasic.FileIO.FileSystem.DeleteDirectory/File(..., RecycleOption.SendToRecycleBin)`，或资源管理器删除）——
  **不许用 `Remove-Item -Force` / `rmSync` / `del` 直接抹掉**（那些绕开回收站 = 不可还原）。**私人数据（`<DSH根>\自我复盘\`）与备份更是碰都别碰**，要处置只能走 `pc-cleanup` 且先在面板说一句。
  ⚠ 反例（当天真发生）：`<个人资料目录>\` 那份 12.1 GB 旧副本被**彻底删除**、回收站里找不到 —— 幸好删前已核对过"新副本 2189 文件 / 12,104.1 MB 与它分毫不差"，否则就是不可逆的数据事故。
- 本地电脑侧的工具（**全部默认空跑，加 `--go` 才动**）：
  `node <DSH根>\工具\清理根目录.mjs`（根目录散文件）· `清理临时目录.mjs`（>7 天临时目录）· `梳理清理.mjs`（死重量：过期安装包/编译缓存/浏览器 profile/spill）；
  处置完在 `引擎\场景项目信息\本地电脑\_文件索引.md` 的「处置记录」写一笔，并追加 `外壳\data\pc-cleanup-log.json`。
- **⚠ 例外（不归它清，谁建的谁收）**：`<DSH根>\工具\`（工具本体）· `<工作区>\_文档\` · 三个入口文件（`README.md` / `_目录地图.md` / `DSH调用逻辑与效率手册.md`）· **各场景自己 `<工作区>\_临时\<会话名>-<时间>\` 里还没过期的**（>7 天才由 `清理临时目录.mjs` 归档）。
- ⛔ 两条红线：**不许替别的场景删它的东西**（要删只能提请求）；顶层是**白名单制**，新建顶层目录要先登记（`<工作区>\_目录地图.md` 表 + `梳理体检.mjs` 白名单，两处一起改）。

### 规矩 9｜「**整树部署 / 整目录同步前必须先验差异**」——★ 差异集合 == 自己改的集合才动手（2026-10-16 `oa-ai` 实测）

- **适用范围（通用，不限 OA、不限部署）**：任何「**把一整棵树推上去 / 盖过去**」的动作 —— 部署、发布、同步、批量覆盖、`robocopy /MIR` 之类；**动手前必须先做一次只读预检**。
- **预检做什么**：把「**本地与目标之间的差异集合**」打出来（**只比对、不上传、不重启**），再对照「**这次我自己改了哪些文件**」。OA 的抓手＝`deploy_backend.py --check-only`。
- **判据（机械的，比"我记得没别人在改"可靠）**：差异集合 **==** 自己的改动集合 ⇒ **才可以真做**；差异里出现**不是自己改的**文件 ⇒ **⛔ 停手**，先通知那个文件的主人 —— `node <DSH根>\工具\派单.mjs --to <会话> --file <消息.md> --go`（照 规矩 8 等回执），**别替它上线**。
- **工程上做不到预检的**：没有 `--check-only` 这类只读开关的部署 / 同步脚本 ⇒ **先补一个预检开关，再部署**（这就是"标准化"该做的事，别拿"这次应该没事"顶）。
- **收尾：部署后再打一次差异** —— 若又冒出**别人的**文件，说明**有并发者在飞**，**立刻互相通知**。★ `oa-ai` 的实测正是这样照出来的：部署完再比对，diff 变成 `quiz.js` / `quizGen.js`，**正好把"另一个代理确实在飞"照出来**。
- **同源道理**：《测试数据规矩》§四 ⑫②「**一个工程不许两个代理同时改**」是同一件事的另一面；**帮手会话（05-协作与规矩/二-标准化规范.md §2.13）并行干活时这条尤其容易踩** —— 多个会话同时在改同一棵树。完整规矩见 `05-协作与规矩/二-标准化规范.md` **§2.14**。

## 补充：回执闭环协议（2026-10-18 宿主亲口改规矩）

> 宿主原话：「改规矩让场景之间可以互相回执聊天，这样才能协作，然后任务做完要通知闭环防止无限聊天」

**★ 三条铁律**

1. **回执必须投递才算闭环**：接单方干完/卡住/干不了，**必须调工具**把回执投回发起方 ——
   `node <DSH根>\工具\通知场景.mjs "<【不需要回执·知悉】结论+证据+落盘路径>" --to <发起方面板id>`
   ⛔ **只在自己窗口里回答 = 没闭环**，发起方收不到（它会以为你还没干完）。
   ⚠ `通知场景` 的正文是**位置参数**（不是 `--file`）；`--file` 只有 `派单.mjs` 支持。
2. **完成即闭环（链路在第 2 条终止）**：回执本身用 `【不需要回执·知悉】` 发出 ⇒ **发起方不再回复**（按规矩"收到知悉一个字都不许回"）。
   只有**确实需要追问/补充**时，发起方才发第 3 条（仍需带标记 + `【结束】`）⇒ 全链路封顶 3 条。
   ⛔ 不要为了"表示收到"再回一条 —— 那正是无限对话的开端（2026-10-18 实测：pc-ai 回执已用知悉发出，我再回就违规）。
3. **防无限（硬上限）**：同一件事全链路 **≤3 条消息**（派单 1 + 回执 1 + 收尾 1）。
   ⛔ 禁止"收到""好的""谢谢"这类纯确认；⛔ 收到 `【不需要回执·知悉】` 一个字都不许回。

**为什么这样能协作又不失控**：
- **能协作**：回执是投递的，发起方一定看得到 ⇒ 任务不会"做完没人知道"；
- **不失控**：收尾那条是 `知悉`（不许回）⇒ 链路必然终止在第 3 条。

**发起方怎么确认对方回没回**（不等消息也能查）：
- `node <DSH根>\工具\待回执.mjs --me <你的面板>` —— 看"发出等回/别人等我"；
- 或直接读对方窗口：`node <DSH根>\工具\读会话尾巴.mjs --to <面板> --tail 8`（**兜底手段**）。

### 补充：发完就结束，不要在 turn 里等（2026-10-18 宿主亲口）

> 原话：「你测试的时候应该发完消息结束，它发过来的自然就到了对话框」

- ✅ **正确**：发完 `通知场景 ... --wake` ⇒ **本 turn 直接结束**；对方回执会作为一条消息进入本会话 inbox，**下一轮自然看到**。
- ⛔ **错误**：在 turn 里 `sleep` 几十秒再 `读会话尾巴` 找回执 —— 既浪费一轮时间，还会**误判**（对方的回执发进我的 inbox，不写在它自己的日志里，翻日志看不到）。
- `读会话尾巴.mjs` 只作**兜底**：对方该回没回、且已经过了很久，再用它去看"它到底在干什么"。
